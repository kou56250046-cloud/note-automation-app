アンケート集計の自動化は、トリガーを1本仕込んだ瞬間に「渡せるもの」と「自分専用」に分かれます。差はコードの出来ではなく、権限の設計です。

この記事の前提

このシステムでは、自由記述の回答をGeminiが読み、感情スコアという数値をシートの1列に書き込む形にしています。

この記事では、そのスコア列がすでに埋まっている状態から始めます。

必要なのは、感情スコアの列と、通知したかどうかを記録する列がもう1つある、という前提だけです。

この記事では、Slack側でのWebhook URLの発行手順そのものは扱いません。すでに1つ発行済みで、その文字列を貼る作業から説明します。

トリガーは「作った人」の権限で動く

GASの時間主導トリガーは、コードを共有しただけでは相手側に生まれません。

相手がスプレッドシートを開いて、自分の画面でトリガーを設定して初めて動き出します。

ここでよく起きるのが、渡した側が「もう動くはず」と思い込んで自分のトリガーだけ残しておくケースです。

壊れる例

こういう状態を想像してください。

自分がトリガーを作り、シートを同僚に共有し、そのまま自分は別の業務に移ります。

トリガーは自分の権限で動き続けるので、シートは毎時更新され、しばらくは何も問題が起きません。

半年後、自分の異動や権限剥奪があった日を境に、通知がぴたりと止まります。

同僚は「なぜ動かなくなったか」を調べる手がかりを持っていません。トリガーの実行者が誰かは、画面から一目では分からないからです。

直す：実行者を確認できる形にする

止まってから気づくのではなく、渡す時点で実行者を確認する手順をセットにします。

スクリプトエディタの「トリガー」画面を開くと、各トリガーの「作成者」列に実行者のアカウントが出ます。

渡す相手が自分のアカウントで新しくトリガーを作り直すのが、いちばん確実な対処です。

自分のトリガーを見せて終わりにせず、相手の画面で同じ手順を一緒に踏んでおきます。

「権限で動く」とは、具体的には次のような意味です。

トリガーが呼ぶ SpreadsheetApp や UrlFetchApp は、トリガーを作成したアカウントの立場でシートを開き、外部にリクエストを送ります。

同僚がそのシートを開いているかどうかは関係ありません。動いているのは、あくまでトリガーを作った本人のアカウントです。

この仕組みを知らずに渡すと、「共有すれば動くはず」という誤解が起きます。共有はシートの閲覧・編集権限を渡すだけで、トリガーの実行権限までは渡しません。

コードから作る：二重登録を防ぐ

トリガー設定は画面からもできますが、他人に渡すシステムでは関数として持たせておくと再現性が上がります。

編集のたびに動くイベントトリガーという選び方もありますが、アンケートの回答は一括で入ってくることが多く、1件ごとの発火は通知が連続する原因になります。

このシステムでは、時間主導トリガーで一定間隔ごとにまとめて確認する形にしています。

ここで壊れやすいのが、次のようなコードです。

// 壊れる例：実行するたびにトリガーが増える
function setupDailyTrigger() {
  ScriptApp.newTrigger('checkNegativeAnswers')
    .timeBased()
    .everyHours(1)
    .create();
}

このコードを2回実行すると、同じ関数を呼ぶトリガーが2つ登録されます。3回押せば3つです。

通知コードが1時間ごとに複数回走り、Slackに同じ内容が重複して届く原因になります。

既存のトリガーを確認してから作る形に直します。

// 直したコード：同じ関数のトリガーがあれば作らない
function setupDailyTrigger() {
  var functionName = 'checkNegativeAnswers';

  var triggers = ScriptApp.getProjectTriggers();
  var alreadyExists = triggers.some(function (t) {
    return t.getHandlerFunction() === functionName;
  });

  if (alreadyExists) {
    Logger.log('トリガーは既に登録済みです。処理を終了します');
    return;
  }

  ScriptApp.newTrigger(functionName)
    .timeBased()
    .everyHours(1)
    .create();

  Logger.log('トリガーを1件作成しました');
}

setupDailyTrigger を1回だけ実行すれば、以後は何度呼んでも増殖しません。

渡す相手にも同じ関数を実行してもらえば、増殖の心配なく自分のトリガーを作れます。

全部通知すると誰も見なくなる

感情スコアがついた回答をすべてSlackに流すやり方も、動くには動きます。

ただしこれをやると、良い評価も悪い評価も同じチャンネルに並び、通知は数日で読み飛ばされる対象になります。

人が反応する通知は、件数が絞られていて、開く理由がはっきりしているものです。

このシステムでは、感情スコアが閾値以下の回答だけを拾います。

拾う件数を減らすことが、通知の中身を薄めない設計そのものです。

「良い評価も含めて全部見たい」という要望が出ることもあります。

その場合でも、Slackへのリアルタイム通知は悪い評価だけに絞り、全件はシート側で見る形をおすすめします。

通知は「今すぐ人が動くべきもの」だけに使い、一覧性が要るものは通知の役割から外します。役割を分けると、両方が機能したままになります。

ネガティブな回答だけをSlackに通知するコード

Slack側であらかじめ発行したIncoming Webhook URLを使います。

URLはコードに直書きせず、スクリプトプロパティに保存します。スクリプトエディタで次の1行を1回だけ実行してください。

function setWebhookUrl() {
  PropertiesService.getScriptProperties().setProperty(
    'SLACK_WEBHOOK_URL',
    'ここに発行したWebhook URLを貼る'
  );
}

通知本体はこちらです。

function checkNegativeAnswers() {
  var sheet = SpreadsheetApp.getActiveSpreadsheet().getSheetByName('回答');
  var data = sheet.getDataRange().getValues();

  // 差し替え箇所：この値以下のスコアだけを通知する
  var THRESHOLD = 2;

  var webhookUrl = PropertiesService.getScriptProperties()
    .getProperty('SLACK_WEBHOOK_URL');

  if (!webhookUrl) {
    Logger.log('SLACK_WEBHOOK_URLが未設定です');
    return;
  }

  for (var i = 1; i < data.length; i++) {
    var comment = data[i][1];
    var score = data[i][2];
    var notified = data[i][3];

    if (score === '' || score > THRESHOLD || notified === '通知済み') {
      continue;
    }

    var payload = {
      text: '低評価の回答を検出しました（スコア ' + score + '）\n' + comment
    };

    var options = {
      method: 'post',
      contentType: 'application/json',
      payload: JSON.stringify(payload)
    };

    UrlFetchApp.fetch(webhookUrl, options);
    sheet.getRange(i + 1, 4).setValue('通知済み');
  }
}

D列に「通知済み」と書き戻すことで、同じ行を次回の実行で再送しないようにしています。

閾値の THRESHOLD は、シートに合わせて数値を差し替える箇所です。5段階評価なら2、10段階評価なら3といった具合に調整します。

つまずきどころ

ここまでの手順で、実際に引っかかりやすい箇所が3つあります。

1つ目は、checkNegativeAnswers を手動実行した直後にトリガーを設定すると、テスト用の通知がそのまま届いてしまう点です。D列の通知済みフラグを一度クリアしてから本番のトリガーを動かすと、テストと本番が混ざりません。

2つ目は、シートの列位置を後から変えたときです。コード内の data[i][2] のような列指定がずれ、感情スコアではない列を読みにいきます。列を動かしたら、対応する数字も見直してください。

3つ目は、Slackの Webhook URL を発行し直したときです。スクリプトプロパティの値を更新し忘れると、古いURLに向けてリクエストが飛び続け、通知だけが届かなくなります。URLを変えたら、setWebhookUrl を書き換えて再度実行してください。

残る手作業

ここまでの仕組みを組んでも、完全に手を離せるわけではありません。

トリガーを作った人が異動や退職で権限を失うときは、次に管理する人が同じ画面で自分のアカウントとしてトリガーを作り直す必要があります。

この引き継ぎだけは、毎回人の手で行う作業として残しておきます。

権限の見直しは、月に一度など決まったタイミングで行うと、引き継ぎ漏れに気づきやすくなります。

今日できること

まずは setupDailyTrigger を自分の環境で1回実行し、トリガー画面に作成者として自分のアカウントが表示されることを確認してください。

これだけで、渡す相手にも同じ手順を説明できる状態になります。

このシステムを他の人に渡すときは、コードを送って終わりにせず、相手の画面でトリガーを作る場面まで一緒に確認しておくことをおすすめします。
