# weekly-build

**1週間分を日曜にまとめて作る。** 週7本＝無料6本（月〜土）＋有料note 1本（日）。

これが note-factory の主フローである。`/note-daily` は1本だけ作り直したいときに使う。

---

## ローカル実行のみ

**クラウド（GitHub Actions / Routines）では実行しない。**

有料noteの `03-draft.md` は `.gitignore` 対象で、クラウドで生成すると手元に残らない。
公開版プレビューの暗号化もローカルでしかできない。

---

## いつ実行するか

**日曜。`market-research` Actions（日曜21時 JST）のあと。**

その週の実測値を見てからテーマを確定できる。
21時より前に実行する場合は、前週のデータで判断することになる旨を `report.md` に記録する。

生成するのは**翌日の月曜から次の日曜まで**の7日分である。日曜に作った有料noteは、
その日ではなく**次の日曜**に投稿する。

---

## 週の並び — 1システムの連載である

**7本は別々のテーマではない。1つの自動化システムを7つに割ったものである。**

| 曜日 | 役割 | type | サブカテゴリ |
|---|---|---|---|
| 月 | 全体設計とデータの入口 | free | 2 |
| 火 | 中核処理（Gemini 呼び出し・変換） | free | 3 |
| 水 | 失敗時の扱い（リトライ・冪等性） | free | 2 |
| 木 | **画面を付ける（HTML Service）** | free | 1 |
| 金 | トリガーと運用（権限・制限・通知） | free | 2 |
| 土 | つまずきポイント集（before → after） | free | 1 |
| 日 | **完成版一式 ＋ 差し替え手順書** | **paid** | 3 |

**各記事は単体で完結させる。** 「前回の続き」で始めない。
前提が必要なら3行で要約し、連載の全体像へのリンクを置く。
連載の3本目だけを検索から踏んだ読者が、その1本で完結できる形にする。

日曜の有料noteは、**その週の無料6本の完成版**である。
無料で部品を見せ、有料で全部入りと差し替え手順書を渡す。
これで `letter-audit` の C3（今買う理由）を**記事構造が作る**。
第2版はレターの文章力で C3 を作っており、W33-07 は2周不合格で打ち切った。

月曜の記事末尾に**その週7本のタイトル一覧**を置く（土曜までの予告）。

---

## 入力

| ファイル | 必須 | 欠けていたら |
|---|:---:|---|
| `research/themes.md` に `status: pending` が **7本以上** | ○ | **停止して `weekly-research` を促す** |
| `knowledge/account.md` | ○ | 停止して `/note-init` を促す |
| `knowledge/voice.md` | ○ | 停止して報告 |
| `knowledge/profile.md` | ○ | 停止して報告（空でよいがファイルは要る） |
| `research/market/{最新}.md` | — | 警告して続行 |

**在庫が7本に満たないときに、その場でテーマを作らない。** 停止する。

pending が7本を超えている場合は、`day` の割り当てと総合スコアの高い順に7本を引く。

---

## 手順

### 1. 在庫から7本引く

```
themes.md の status: pending を全部読む
  ↓
day が割り当てられているものを、その曜日に置く
  ↓
day が無いものを、スコアの高い順に空いた曜日へ入れる
  ↓
日曜（paid）には支払い意欲4以上のテーマを置く
  → 該当が無ければ paid を作らず、無料7本にして報告する
```

`slug` は `YYYY-MM-DD-{英数字の短い識別子}`。**日付は投稿予定日**であって生成日ではない。

各記事に `notes/{slug}/00-theme.md` を書く。

### 2. 無料6本を並列で書く

**`writer` サブエージェントを6つ同時に起動する。** 1本ずつ順に作らない。

各 `writer` に渡すもの。

- `.claude/skills/editorial/daily-article/SKILL.md`（記事の型のすべて）
- `research/themes.md` の該当エントリ全文
- `knowledge/account.md` / `profile.md` / `voice.md`
- slug・publishDate・カテゴリ・ハッシュタグ
- **同じ週の他の記事との差別化の指示**（dedup を通すため）
- **同じ週の既存記事との重複を避けるため、読ませる既存記事のパス**

**渡してはいけないもの: 出来の良し悪しの判断。** `writer` は書くだけである。

**サブ①（木曜の画面・土曜のつまずき集）には `demo/before.html` と `after.html` も作らせる。**
連載では毎週この2本が該当する。木曜は自動化システムの画面そのもの、
土曜は詰まりどころの before/after を並べる。
**外部ライブラリ・CDN・外部フォント・外部画像を使わせない**（Pages の CSP で落ちる）。

### 3. 決定論ゲートを全件に通す

```bash
python scripts/lint.py notes/*/01-draft.md
python scripts/dedup.py --all
```

**error があれば直す。** `failures` だけを `writer` に返す。**全文の書き直しを指示しない。**

よく出るもの。

- `char-count` 本文が2500字を下回る → **コードを増やさせない。本文を足させる**
- `sentence-length` 100字超は error
- `heading-skip` H1 から H3 に飛んでいる
- `no-artifact` 実物が無い → テーマ選定が間違っている。停止して報告する

### 4. ethics-line は検出時のみ（無料記事）

`lint.py` の `needsAudit` が `true` の記事だけ `auditor` を起動する。
`false` なら呼ばない。**これはゲートを緩めたのではなく、判定を決定論コードへ移した結果である。**

### 5. reader-feedback は週1本だけ

**月曜の記事に掛ける。** `critic` を1回だけ起動する。

指摘があれば `failures` だけを `writer` に返して修正する。

### 6. 有料noteを作る（日曜分）

**ここだけは順番を飛ばせない。**

```
1. product-concept       → 00-concept.md（productType を必ず確定）
2. pricing-strategy      → pricing.json（価格 + 天井 + 根拠）
3. sales-letter          → 02-letter.md, letter-meta.json
4. draft-writing         → 03-draft.md（★追跡しない）
5. letter-audit          最大2周
6. ethics-line（full）   上限なし
7. title-design          → 07-titles.md
```

#### 価値軸は「減算ではない軸」を必ず1本入れる

**過去2件の商品が、同じ理由で A1 を落としている。**

価値軸を5本立てても、名前が違うだけで全部「書き手の作業工程が減る」に帰着すると、
理想の未来が「〜がなくなる／要らない」の否定形に収束して A1 が通らない。

`00-concept.md` の価値軸に、**到達・獲得の軸を最低1本**入れること。
例: 「スクリーンショットをそのまま人に送れる。相手が見るのは自分が決めた色である」。

#### C3（今買う理由）には本物の期限しか使えない

偽の期限・先着・数量限定は `ethics-line` の E1（景品表示法）に当たる。

**書けるのは実行する予定のある値上げだけである。**
`pricing.json` の `priceSchedule` に日付と金額を登録し、`letter-meta.json` の
`deadlineClaims` に記録して `ethics-line` の検査に通す。

**実行は人間の作業である。** リポジトリにリマインドの仕組みは無い。
値上げしないと決めた場合は、判断より先にレターの該当行を販売ページから削除する。

#### 同梱するコードは実際に走らせる

`03-draft.md` に載せたスクリプトは、**抽出して実行して確認する。**

過去に、正しい使い方が誤検出される実装バグを載せたまま出しかけた例がある。
`ethics-line` が静的追跡で拾ったが、本来は執筆側で実行して確認すべきものである。

### 7. 仕上げ

```
1. thumbnail-prompt → 各記事の 06-thumbnail.md（★記事が確定してから）
2. build-report     → 各記事の report.md
3. themes.md の該当エントリを status: used に更新
4. node scripts/build-demo.mjs（demo があるとき）
5. git add / commit / push
```

**`03-draft.md` は `.gitignore` で除外されるため push に含まれない。** 正常である。

### 8. プレビューを出す

```
/note-preview
```

有料部分の暗号化・投稿済みの除外・ダッシュボードの更新が、ここでまとめて行われる。

---

## 報告の形式

```
今週の7本ができました（{開始日} 〜 {終了日}）

| 曜日 | slug | 種別 | 字数 | lint | dedup |
|---|---|---|---|---|---|
| 月 | ... | 無料 | 2800 | 0 | 0.00 |
...
| 日 | ... | 有料 {price}円 | — | 0 | — |

## ゲート
reader-feedback（月曜の1本）: 指摘 {n} 件 → 修正済み
ethics-line: 起動 {n} 本 / 検出 {n} 件
letter-audit: {n}/16（round {n}）

## 書けなかったこと
- {profile.md に根拠がなく諦めた主張}

## 人間の作業
- {値上げの実行予定など、自動化されていないもの}

## weekly-research への申し送り
- {sources が足りなかった、など}

次: /note-preview でコピーして note に貼れます。
```

---

## 絶対に守ること

- **web 検索をしない。** 在庫から引くだけである。調べたくなったら `report.md` に申し送りを書く
- **在庫が7本未満なら停止する。** その場でテーマを作らない
- **自己評価しない。** 「良い記事ができました」と書かない。ゲートの結果だけを報告する
- **`profile.md` にない実績を書かない。** 足りなければ「書けなかったこと」に記録する
- **クラウドで実行しない。** ローカルのみ
- **確認を求めるために処理を止めない。** 止めてよいのは入力ファイルが欠けているときだけ
