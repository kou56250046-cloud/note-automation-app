# daily-article

無料記事を1本書く。**週6本（月〜土）の主力。**

日曜の `/note-week` が、このスキルを単位として `writer` を6つ並列起動する。

---

## `writer` サブエージェントで実行する

執筆に集中させ、判定させない。出来の良し悪しは `critic` と `auditor` が判断する。

---

## web 検索をしない

**在庫から引くだけである。** これが毎日投稿を成立させている理由である。

調べたくなったら、それは在庫の `sources` が足りていない。
その場で検索せず、`weekly-research` への申し送りとして `report.md` に記録する。

---

## 入力

| ファイル | 必須 | 何に使うか |
|---|:---:|---|
| `research/themes.md` | ○ | 今日のテーマ |
| `knowledge/account.md` | ○ | ペルソナ・カテゴリ・投稿方針 |
| `knowledge/profile.md` | ○ | **「書けないこと」** |
| `knowledge/voice.md` | ○ | 文体・禁止表現 |

1つでも欠けたら**停止して、不足ファイル名を報告する。** 推測で埋めない。

---

## テーマの引き方

```
1. themes.md から status: pending かつ day が今日の曜日のものを探す
2. 見つかった → それを使う
3. 見つからない → pending のうち type: free で最もスコアが高いものを使う
4. pending が1本もない → 停止する
```

**在庫が空のときに、その場でテーマを作らない。** 停止して `weekly-research` の実行を促す。

引いたら `notes/{slug}/00-theme.md` にコピーし、なぜ今日これを選んだかを1文添える。

`slug` は `YYYY-MM-DD-{英数字の短い識別子}` とする（例: `2026-08-10-skill-frontmatter`）。

---

## 記事の型

**2500〜4000字。** コードブロックを除いた本文で数える（`lint.py` の `char-count`）。

実物を載せる余地を確保するために広げてある。**コードで水増ししない。**

```
1. フック          結論を先に置く。1〜2文
2. 問題の可視化    読者が昨日か今日やった（やらなかった）動作を書く
3. 本題            手順・具体例・設定値。ここが記事の中身
3.5 実物           ★必須。プロンプト全文 / コード全文 / before→after
4. つまずきどころ  実際に引っかかる箇所を1〜2個
5. 今日できること  読者がこの記事を読んで最初にやること。1つだけ
6. 締め            次に繋がる一文
```

### 1. フック — 結論を先に置く

```
✕ 「今回は◯◯について説明します」        → 何も言っていない
✕ 「◯◯をご存知でしょうか」              → 引き延ばし
○ 「◯◯は設定1行で解決します。3日調べた結論です」
```

### 2. 問題の可視化 — 行動で名指しする

**状態で書くと他人事になる。行動で書くと自分の話になる。**

```
✕ 「設定に困っている人」                  → 状態
○ 「同じ設定を3回書き直して、まだ動いていない人」  → 行動
```

### 3. 本題 — 具体性で価値を出す

**実績がないアカウントの無料記事は、具体性でしか価値を出せない。**

| 出せる価値 | 出せない価値 |
|---|---|
| 手順（何を、どの順で） | 「私はこれで成果を出した」 |
| 設定値・コード・コマンドの実物 | 「多くの人に効果があった」 |
| つまずいた箇所とその回避 | 「これが最も効率的だ」（比較検証していない） |
| 公式ドキュメントに書かれていない挙動 | 収益・時間削減の数値 |

**網羅しない。1点を深く書く。** 「◯◯の全て」より「◯◯のこの1箇所」のほうが読まれる。

### 3.5 実物 — これが無い記事は書き上げない

**次の3つのうち最低1つを、省略せず全文で載せる。**

| 実物 | 条件 |
|---|---|
| **プロンプト全文** | コピーしてそのまま動く形。「〜のように指示します」で済ませない |
| **コード全文** | HTML/CSS/GAS。断片ではなく**動く単位**で出す |
| **before → after** | デモURLとコードの両方。片方だけでは足りない |

**実物が用意できないなら、テーマ選定のほうが間違っている。**
書き上げずに停止し、`report.md` に理由を記録して `weekly-research` へ差し戻す。

`scripts/lint.py` の `no-artifact` が機械判定する（**error**。記事を通さない）。
デモURL（`/demo/` を含む）が本文にあれば、コードブロックが無くても通る。

### サブカテゴリ別の実物の形

| サブカテゴリ | 何を載せるか |
|---|---|
| **1. AI×Webデザイン** | before/after のデモURL ＋ 変更点の CSS/HTML ＋ 指示したプロンプト全文 |
| **2. Gemini+GAS** | GASコード全文 ＋ プロンプト全文 ＋ 動作条件（トリガー・権限・実行制限） |
| **3. NotebookLM・精度向上** | 設定とプロンプトの全文 ＋ 適用前後の出力の実物 |

**「出し惜しみ」をしない。** 無料記事で実物を出すことが、有料noteの信用になる。

### 5. 今日できること — 1つだけ

**3つ置くと人は何もやらない。** 1つに絞る。

## 書いてはいけないこと

**`profile.md` の「書けないこと」セクションを必ず読む。**
そこに列挙された主張は、言い換えても書かない。

| ✕ | ○ 代わりに |
|---|---|
| 「これで月◯万円になりました」 | 手順そのものの説明 |
| 「◯人が使っています」 | 何ができるかの説明 |
| 「作業時間が◯%減りました」 | どの作業が不要になるかの説明 |
| 「これが一番効率的です」 | 「私はこう書いている」と限定する |
| 「必ず」「絶対に」「誰でも」 | 条件を明示する（`voice.md` の ng） |

**足りないものを埋めるために創作しない。** 書かずに `report.md` に「足りない」と記録する。

**数値を伴わない作業の描写は書いてよい。**

```
○ 「毎回手でコピペしていた」          → 作業の描写
○ 「同じ設定を3回書き直した」          → 同上
✕ 「これで作業時間が半分になった」      → 成果の主張。profile.md が要る
```

---

## カテゴリの範囲を出ない

`account.md` の主カテゴリ1つ＋サブカテゴリ2〜3つの外は書かない。

範囲を出ると、その記事だけでなく**アカウント全体の推薦が弱くなる。**

---

## タイトル

**無料記事のタイトルはここで決める。**（`title-design` は有料note専用）

| 条件 | 理由 |
|---|---|
| 30〜40文字 | note の一覧で切れない長さ |
| 具体的な数字か固有名詞を1つ入れる | 抽象的なタイトルは選ばれない |
| 読者の行動を名指しする | 「自分のことだ」と感じさせる |
| `voice.md` の ng に該当しない | 煽らない。`lint.py` が検出する |

```
✕ 「効率化のすすめ」                      → 抽象的
✕ 「知らないと損する◯◯」                 → 煽り（ng）
✕ 「【衝撃】AIデザインの正体」            → 煽り（ng）
○ 「Claude Code に作らせた管理画面の余白を、3箇所だけ直した before/after」
○ 「Gemini + GAS で議事録を要約する。プロンプトとコードの全文」
```

**煽り型を使わない。** 実測では煽り型のほうがスキ中央値が1.8倍高いが
（`learnings.md` の「タイトル型の実測」）、方針として使わない。

読者層がエンジニア・制作者寄りであること、具体物型のほうが p90 で2倍以上
上振れすることが理由である。デザイン系タグに限れば差はほぼ無い。

---

## note で崩れる記法を使わない

| 記法 | 可否 |
|---|---|
| 見出し（H2 / H3）・太字・引用・水平線 | ○ |
| 箇条書き（2階層まで） | ○ |
| コードブロック | ○（言語指定は貼付後に手動で設定する） |
| **テーブル** | **✕ note が非対応。箇条書きにする** |
| 脚注・3階層以上のリスト | ✕ |

`lint.py` が検出するが、書く時点で避ける。

## 出力

### `notes/{slug}/00-theme.md`

```markdown
# {テーマ}

themes.md の id: 2026-W33-01
選定理由: {themes.md の rationale をコピー}
今日これを選んだ理由: {曜日の割り当てどおり / 在庫の都合で繰り上げ など}

## 切り口
{themes.md の angle}

## 出典
{themes.md の sources}
```

### `notes/{slug}/01-draft.md`

本文。**タイトルは含めない**（`meta.json` に入れる）。

### `notes/{slug}/meta.json`

```json
{
  "slug": "2026-08-10-admin-ui-spacing",
  "themeId": "2026-W33-01",
  "type": "free",
  "title": "Claude Code に作らせた管理画面の余白を、3箇所だけ直した before/after",
  "category": "生成AIで見せられる成果物を作る / AI×Webデザイン",
  "hashtags": ["Webデザイン", "UIデザイン", "LP制作", "生成AI"],
  "demo": "https://kou56250046-cloud.github.io/note-automation-app/demo/2026-08-10-admin-ui-spacing/",
  "artifacts": ["beforeAfter", "code", "prompt"],
  "publishDate": "2026-08-10",
  "charCount": 3100,
  "createdAt": "2026-08-10T06:00:00+09:00"
}
```

| フィールド | 内容 |
|---|---|
| `demo` | デモページのURL。無ければ `null` |
| `artifacts` | 載せた実物の種類。`"code"` / `"prompt"` / `"beforeAfter"` から1つ以上 |

**`artifacts` が空の `meta.json` を書かない。** 空になるなら記事が成立していない。

### ハッシュタグ

**3〜5個。** 多いと薄まる。**`account.md` の「ハッシュタグ」節の既定に従う。**

タグの選び方で到達が2桁変わる。空白タグ（`Webデザイン` `UIデザイン` `GAS`
`GoogleAppsScript` `NotebookLM` `LP制作`）を主軸にする。

`ClaudeCode` `AI活用` `AIエージェント` `業務効率化` は**主軸にしない**。
需要÷供給が 0.02〜0.06 で、1日400件以上に押し流される。添えるなら1つまで。

### `themes.md` の更新

引いたエントリの `status` を `pending` → `used` に変更する。

## 書き終えたら

**自己評価しない。** そのまま次に渡す。

```
1. scripts/lint.py と scripts/dedup.py を実行する      ← トークン0
     ↓
2. error があれば直す（no-artifact / note-table / ng-expression など）
     ↓
3. lint の needsAudit が true のときだけ ethics-line（auditor）を起動する
   false なら auditor を呼ばない
     ↓
4. reader-feedback（critic）は週1本だけ。日曜の有料note生成に併せて実行する
     ↓
5. thumbnail-prompt → 06-thumbnail.md（見出し画像のプロンプト）
     ↓
6. build-report → report.md
```

**`thumbnail-prompt` は記事が確定してから実行する。** 本文が変われば被写体も変わる。
`demo/after.html` があるときは、そこから配色を取って記事とサムネの色を揃える。

### なぜ毎回 critic と auditor を呼ばないのか

**判定を消したのではない。LLM から決定論コードへ移した**（CLAUDE.md ルール1）。

- E5（断定表現）は `voice.md` の `ng` を `lint.py` が部分一致で潰している
- E3（裏付けのない実績）は `lint.py` の `unverified-claim` が金額・割合・人数・
  期間・フォロワー数のパターンで拾う。**拾ったら auditor に回す**

無料記事で毎回 Opus を呼ぶのをやめ、疑いが出たときだけ呼ぶ。
週5回の Opus 呼び出しが、ほぼ0になる。

**有料noteは従来どおり `letter-audit` と `ethics-line` を必ず実行する。**
売る以上は景表法・特商法のリスクが実在するため、ここは削らない。

### この設計で漏れるもの

**数値を伴わない婉曲な実績主張は機械では拾えない。**
「思ったより早く終わりました」のような示唆は `unverified-claim` に掛からない。

週1本の `reader-feedback` と月次レビューで検出する。
漏れを承知のうえでコストを取っている、という判断である。

「良い出来かどうか」を自分で結論しない。それは `critic` と `auditor` の仕事である。

---

## report.md に必ず記録すること

- 引いたテーマと選定理由
- **書けなかったこと**（`profile.md` に根拠がなく諦めた主張）
- `weekly-research` への申し送り（`sources` が足りなかった、など）
- 各ゲートの結果は後続スキルが追記する
