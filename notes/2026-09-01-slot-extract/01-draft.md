自由記述の「都合」欄を、そのままGeminiに要約させても、後段では使えません。

必要なのは要約でも分類でもなく、曜日×時間帯のboolean配列への変換です。この記事では、その変換だけをこの1本で再現できるところまで書きます。

「火水木ならいつでも」という1文を読むたびに、曜日と時間帯を頭の中で変換して、シートに手で入力していませんか。回答が10件を超えると、この変換だけで手が止まります。

## 前提 — この記事だけで動くこと

前提はこの3行です。

- スプレッドシートに `responses` シートがあり、`都合` 列に自由記述が1件入っている
- `DAYS`・`SLOTS`・`GEMINI_MODEL` の定数は、あとのコード内にそのまま書いてある
- Gemini APIのキーは、まだどこにも登録していない

この3行さえ満たしていれば、他の記事を読んでいなくても、この先を再現できます。

シートの列構成や、処理状態を`pending`から`done`に変える処理は、別の記事の範囲です。ここでは1件のテキストをGeminiに渡し、構造化されたJSONを受け取るところまでに絞ります。

失敗したときのリトライや、同じ行を二重に処理しない排他制御も、ここでは扱いません。この記事の担当は、あくまで自由記述を1回変換するところまでです。

## 分類でも要約でもない。抽出・正規化

「火水木ならいつでも」「月曜の午前だけ無理」のような自由記述を、Geminiに読ませて何を返させるか。ここで選ぶのは、要約でも固定ラベルへの分類でもありません。

要約は出力が自由文なので、多少の表現の揺れを許容できます。分類は決まった選択肢のどれかを選ぶ作業です。

今回はどちらとも違います。曜日と時間帯の組み合わせを、あらかじめ決まった「箱」に、trueかfalseで埋めていく作業です。

箱の数は固定です。平日5日×時間帯3つで、15個のbooleanが必ず埋まります。

後段の画面は、`mon.am`のようなキーを直接参照してマスに色を塗ります。1つでも欠けると、その1マスだけ描画できずに処理が止まります。

この「キーが絶対に欠けない」という制約が、要約や分類には無かったものです。要約は文字数が多少ずれても実務に支障はありません。分類も未分類というラベルで逃げられます。

今回はそれができません。15個のキーすべてに、必ず何らかの真偽値が入っている必要があります。

## 曖昧語で壊れる場所

自由記述には、時間帯を明示しない書き方がたくさん出てきます。

「いつでも」は全部の時間帯がtrueという意味です。「夕方以降」は夜の枠だけがtrueという意味です。この対応関係をGemini側の解釈に任せると、呼び出すたびに違う判定が返ってきます。

もう1つ壊れやすいのが否定表現です。「都合が悪い」「厳しい」は、参加できないという意味です。

しかし、この言い回しだけでは、曜日名と単語が近くにあることを、モデルが単なる言及だと解釈し、trueと判定することがあります。

さらに厄介なのが、まったく触れられていない曜日の扱いです。「火水木ならいつでも」とだけ書かれた場合、月と金には何も書かれていません。

ここをtrueにしてしまうと、実際には空いていない枠まで空きとして扱われます。

これらのルールは、Geminiの判断に委ねず、プロンプト側に明示しておく必要があります。書かなければ、同じ入力でも呼び出すたびに解釈が変わります。

## プロンプト全文

コピーしてそのまま使えます。`{{ここに自由記述のテキストを差し込む}}` の部分だけ、シートから読んだ値に置き換えます。

```
あなたはスケジュール調整の担当者です。
以下の自由記述から、平日5日(月・火・水・木・金)×3つの時間帯
(午前・午後・夜)ごとに、参加できるかどうかを判定してください。

次のルールに従ってください。
1. 各曜日について、午前・午後・夜の3つすべてにtrueかfalseを必ず入れる。省略しない。
2. 「いつでも」「終日OK」のように時間帯の指定なしに曜日だけが
   空いていると読める場合は、その曜日の3つすべてをtrueにする。
3. 「午前中は無理」「午後から」のように時間帯の指定がある場合は、
   指定された時間帯だけをその真偽値にする。
4. 「夕方以降」「夜だけ」は夜(eve)のみtrueとし、午前・午後はfalseにする。
5. 「都合が悪い」「厳しい」「無理」「参加できない」は、
   その曜日・時間帯をfalseにする否定表現である。肯定の言葉と読み違えないこと。
6. 「火水木ならいつでも」のように複数の曜日をまとめて指定している場合は、
   列挙されたすべての曜日に同じ判定を適用する。
7. 自由記述の中でまったく触れられていない曜日・時間帯は、
   すべてfalseにする(空いているとは判断しない)。
8. 土日への言及は無視する。
9. 出力はJSON形式のみとし、説明文や前置きを含めない。
10. 曜日のキーはmon, tue, wed, thu, friの英語表記を使う。

自由記述:
"""
{{ここに自由記述のテキストを差し込む}}
"""
```

7番目の「言及の無い曜日をfalseにする」ルールが、この記事でいちばん重要な1行です。ここを書かないと、「触れていない=空いている」と誤読されるケースが出ます。

## responseSchemaとUrlFetchAppの呼び出しコード全文

プロンプトだけでは、出力の型までは固定できません。`generationConfig`に`responseSchema`を渡して、曜日と時間帯のすべてのキーを`required`に指定します。

```javascript
// config.gs にまだ無ければ、この3行を追加する
const DAYS = ['mon', 'tue', 'wed', 'thu', 'fri'];
const SLOTS = ['am', 'pm', 'eve'];
const GEMINI_MODEL = 'gemini-2.5-flash';

/**
 * 自由記述をGeminiに渡し、曜日×時間帯のboolean配列を受け取る。
 */
function extractAvailability(freeText) {
  const apiKey = PropertiesService.getScriptProperties().getProperty('GEMINI_API_KEY');
  if (!apiKey) {
    throw new Error('スクリプトプロパティに GEMINI_API_KEY がありません');
  }

  const url = 'https://generativelanguage.googleapis.com/v1beta/models/'
    + GEMINI_MODEL + ':generateContent?key=' + apiKey;

  // 時間帯側のスキーマ。am / pm / eve の3つを全部requiredにする
  const daySchema = {
    type: 'OBJECT',
    properties: SLOTS.reduce(function (props, slot) {
      props[slot] = { type: 'BOOLEAN' };
      return props;
    }, {}),
    required: SLOTS
  };

  // 曜日側のスキーマ。mon〜friの5つを全部requiredにする
  const schema = {
    type: 'OBJECT',
    properties: DAYS.reduce(function (props, day) {
      props[day] = daySchema;
      return props;
    }, {}),
    required: DAYS
  };

  const payload = {
    contents: [
      { role: 'user', parts: [{ text: buildPrompt_(freeText) }] }
    ],
    generationConfig: {
      responseMimeType: 'application/json',
      responseSchema: schema
    }
  };

  const options = {
    method: 'post',
    contentType: 'application/json',
    payload: JSON.stringify(payload),
    muteHttpExceptions: true
  };

  const response = UrlFetchApp.fetch(url, options);
  const status = response.getResponseCode();

  if (status !== 200) {
    throw new Error('Gemini API がエラーを返しました: ' + status + ' ' + response.getContentText());
  }

  const body = JSON.parse(response.getContentText());
  const jsonText = body.candidates[0].content.parts[0].text;
  return JSON.parse(jsonText);
}

function buildPrompt_(freeText) {
  return 'あなたはスケジュール調整の担当者です。\n'
    + '以下の自由記述から、平日5日(月・火・水・木・金)×3つの時間帯\n'
    + '(午前・午後・夜)ごとに、参加できるかどうかを判定してください。\n\n'
    + '次のルールに従ってください。\n'
    + '1. 各曜日について、午前・午後・夜の3つすべてにtrueかfalseを必ず入れる。省略しない。\n'
    + '2. 「いつでも」「終日OK」のように時間帯の指定なしに曜日だけが\n'
    + '   空いていると読める場合は、その曜日の3つすべてをtrueにする。\n'
    + '3. 「午前中は無理」「午後から」のように時間帯の指定がある場合は、\n'
    + '   指定された時間帯だけをその真偽値にする。\n'
    + '4. 「夕方以降」「夜だけ」は夜(eve)のみtrueとし、午前・午後はfalseにする。\n'
    + '5. 「都合が悪い」「厳しい」「無理」「参加できない」は、\n'
    + '   その曜日・時間帯をfalseにする否定表現である。肯定の言葉と読み違えないこと。\n'
    + '6. 「火水木ならいつでも」のように複数の曜日をまとめて指定している場合は、\n'
    + '   列挙されたすべての曜日に同じ判定を適用する。\n'
    + '7. 自由記述の中でまったく触れられていない曜日・時間帯は、\n'
    + '   すべてfalseにする(空いているとは判断しない)。\n'
    + '8. 土日への言及は無視する。\n'
    + '9. 出力はJSON形式のみとし、説明文や前置きを含めない。\n'
    + '10. 曜日のキーはmon, tue, wed, thu, friの英語表記を使う。\n\n'
    + '自由記述:\n"""\n' + freeText + '\n"""';
}
```

`required`を曜日の配列と時間帯の配列の両方に指定しているのがポイントです。

曜日側だけ`required`にすると、`mon`キーの中身が空オブジェクトで返ってきても、スキーマの検証は通ってしまいます。時間帯側にも`required`を入れると、15個のキーすべてが埋まっている状態を保証できます。

## つまずいた場所

`responseSchema`をネストした`OBJECT`にするとき、外側の`required`だけ書いたことがあります。内側の`daySchema`に`required`を書き忘れていました。

その状態だと、Geminiは`{"mon": {}}`のような空オブジェクトを返してもエラーになりません。あとでシートに書き込むコードが`undefined`を参照して落ちるまで、原因に気づけませんでした。

ネストしたスキーマでは、外側と内側の両方に`required`を指定する必要があります。片方だけでは足りません。

もう1つは、否定表現の誤判定です。プロンプトに5番のルールを入れる前は、「木曜は都合が悪いです」という記述に対して、木曜の枠がtrueで返ってくることがありました。

「都合」という単語と曜日が近くにあることを、肯定的な言及と読み違えていたようです。否定語を具体的に列挙してからは、この誤判定は起きなくなりました。

## 今日できること

`PropertiesService`のスクリプトプロパティに、`GEMINI_API_KEY`という名前でAPIキーを1つ登録してください。

登録できたら、`extractAvailability`関数に自由記述を1件渡してください。例えば「火水木ならいつでも、木曜だけ都合が悪いです」のような文です。

実行ログでJSONの形を確認できます。15個のキーがすべて入っているか、木曜だけfalseになっているかを見てください。

APIキーが未登録のまま実行すると、`extractAvailability`はその場でエラーを投げて止まります。

出力の型を固定しておくと、この先の工程が壊れにくくなります。次は、この呼び出しが失敗したとき、あるいは同じ行を二重に処理してしまったときに、どう扱うかを書きます。
