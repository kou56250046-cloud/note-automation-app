ヒートマップは、色の濃淡だけで状態を伝える画面です。

情報量が増えるほど、濃淡の差が読み取りにくくなります。

日程調整のヒートマップを、参加者24人・5日×3コマの規模で表示したときに崩れる5箇所を、before→afterのコードでそのまま直します。

このシステムは、フォームの自由記述をGeminiで「曜日×時間帯の空き/不可」に構造化し、HTML Serviceのヒートマップ画面で幹事に見せる仕組みです。

この記事は、そのヒートマップを人数の多い名簿で表示したときに起きる、見た目の崩れだけを扱います。

仕組みの作り方を読んでいなくても、GASでグリッド状の画面を公開しているなら踏む可能性がある崩れなので、この1本で完結します。

before/afterは下のURLで、実際に動く状態のまま並べて確認できます。

https://kou56250046-cloud.github.io/note-automation-app/demo/2026-09-05-heatmap-pitfalls/

1. 参加者が20人を超えると、セルが縦に潰れて色の差が見えなくなる

5人分を前提にするなら、CSS Gridの行をrepeat(N, 1fr)にして、コンテナの高さを固定する書き方で足ります。

人数が少ないうちは1行が十分な高さになります。しかし参加者が24人に増えると、同じ高さの中に24行を押し込むことになります。

高さ460pxのうち30pxはヘッダー行なので、残る430pxを24行で割ると1行は18px前後にしかなりません。空きと不可の色の差は線のように細くなり、見分けにくくなります。

原因は、行の高さを「コンテナの高さ÷行数」で決めていたことです。行数が増えるほど、1行あたりの高さが下がり続けます。

before（高さを固定し、行を均等割りする）

.heatmap-grid {
  display: grid;
  grid-template-columns: max-content repeat(15, 1fr);
  grid-template-rows: 30px repeat(24, 1fr);
  height: 460px;
}

after（行の最小高さを固定し、超えた分は縦スクロールに逃がす）

.heatmap-scroll {
  max-height: 420px;
  overflow-y: auto;
}

.heatmap-grid {
  display: grid;
  grid-template-columns: 112px repeat(15, 44px);
  grid-auto-rows: 32px;
}

grid-template-rowsをやめてgrid-auto-rowsにすると、行の高さは人数に関係なく32pxで固定されます。

人数が増えた分は、コンテナのoverflow-y: autoが縦スクロールとして受け止めます。行の高さを固定してから、はみ出す分の逃がし先を用意する、という順番が要点です。

2. 空き・不可・未回答の3段階しかないのに、濃淡が連続的で読みにくい

状態は「空き」「不可」「未回答」の3つしかありません。ところが色を決める関数が、行番号と列番号から明度を連続的に変化させる作りになっていることがあります。

同じ「空き」のセルでも、隣同士でわずかに色が違います。目が「同じ状態のまとまり」を探そうとするたびに、余計な濃淡差に邪魔されます。

これは3段階のデータを、連続値向けの色付けロジックで塗っていることが原因です。状態の種類と、色の作り方が一致していません。

before（行・列のインデックスから明度を連続的に決めている）

function colorFor(status, pi, si) {
  var hue = status === 'available' ? 125 : 5;
  var l = 42 + ((pi * 5 + si * 3) % 18);
  return 'hsl(' + hue + ',55%,' + l + '%)';
}

after（3状態を3色に固定し、凡例を添える）

var COLOR = {
  available: '#1971c2',
  unavailable: '#e8590c',
  unanswered: '#ced4da'
};

function colorFor(status) {
  return COLOR[status];
}

色の種類を状態の種類と同じ数まで減らすと、目で追う対象が3種類だけになります。

3色の選び方にも条件があります。空きを緑、不可を赤にするのは直感的ですが、赤と緑は見分けにくい人がいる組み合わせです。状態の区別をこの2色に預けると、その人には全部が同じ色の面に見えます。

青とオレンジであれば、色の差が残ります。凡例を画面に添えておくと、どちらが「空き」かを画面の中で確認できます。ヒートマップは色に意味を乗せる画面なので、色数を絞ることと、絞ったあとの2色を何にするかが、そのまま読みやすさになります。

3. スマホ幅で曜日の列がはみ出す

5日×3コマ、合計15列を並べると、PCの画面幅では収まっても、スマホの画面幅では収まりません。

コンテナの幅を固定していると、はみ出した列はそのまま画面の外に切れて見えなくなります。

before（幅を固定し、はみ出し方向の対処をしていない）

.heatmap-wrap {
  width: 900px;
}

after（横スクロールを許可し、行ラベルの列を固定する）

.heatmap-scroll {
  width: fit-content;
  max-width: 100%;
  overflow-x: auto;
}

.cell.label {
  position: sticky;
  left: 0;
}

overflow-x: autoを親要素に指定すると、幅が足りない分は横スクロールで見えるようになります。

ただし横スクロールだけでは、スクロールした先で「誰の行か」が分からなくなります。そこで行ラベルの列にposition: sticky; left: 0;を指定し、スクロールしても左端に固定されるようにしています。

4. 参加者名が長いと、行ラベルがヒートマップ本体を圧迫する

役職や補足が付いた名前があると、行ラベルの列の幅がその名前に合わせて伸びます。

before（max-contentは最も長い名前に幅を合わせる)

.heatmap-grid {
  grid-template-columns: max-content repeat(15, 1fr);
}

その結果、名前が長い1人のために、24人分のセルの幅が全体的に狭くなります。

after（列幅を固定し、省略表示にしてホバーとフォーカスで全体を出す）

.cell.label {
  width: 112px;
  white-space: nowrap;
  overflow: hidden;
  text-overflow: ellipsis;
}

.cell.label:hover::after,
.cell.label:focus::after {
  content: attr(data-full);
  position: absolute;
  background: #333;
  color: #fff;
  padding: 4px 8px;
}

列幅を数値で固定し、はみ出した文字列はtext-overflow: ellipsisで省略します。

全体の名前は、data-full属性に入れておいた文字列を::afterで表示する形にしました。マウスのホバーだけでなく、tabindex="0"を付けてキーボードのフォーカスでも同じ表示が出るようにしています。キーボード操作だけで確認する人にも、名前の省略が壁にならない形です。

5. Web Appのデプロイ設定が「自分のみ」のままで、共有相手が開けない

ここだけはコードの話ではなく、GASのデプロイ設定の話です。

Web Appを「新しいデプロイ」で公開するとき、「アクセスできるユーザー」という項目があります。既定値は「自分のみ」です。

自分の画面では普通に開けるので、この設定に気づかないまま参加者にURLを配ってしまいがちです。参加者側では「アクセスできません」という表示になり、ヒートマップにたどり着けません。

修正は、デプロイ設定の画面で「アクセスできるユーザー」を「全員」または組織内向けの範囲に変更するだけです。コードの変更は要りません。

出典: https://developers.google.com/apps-script/guides/web

この設定は画面には出ないので、上のデモではヒートマップの下に注意書きを常設し、共有前に確認する箇所として明示しています。ここは自動化できず、デプロイのたびに手作業で確認する箇所として残ります。

今日できること

まず、公開しているヒートマップのURLを、自分以外の端末かブラウザのプライベートウィンドウで開いてください。

開けなければ、デプロイ設定の「アクセスできるユーザー」を確認するところから始めます。

開けたら、次にスマホの実機かブラウザの検証ツールで幅を狭くし、行ラベルの列が固定されたまま横スクロールできるかを確認してください。

見た目の崩れの多くは、参加人数が少ない開発中には出ません。今日、実際の人数に近い状態で開いて初めて見えてきます。

おわりに

今回の5箇所は、どれもテスト段階の少人数では表に出ず、参加者が増えたり、共有したりして初めて表面化する種類のものです。

色の段階を絞ること、行の高さを固定してから逃がし先を用意すること、共有範囲の設定を確認すること。この3つを押さえておくと、人数が変わっても崩れにくい画面になります。
