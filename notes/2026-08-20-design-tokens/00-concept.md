# コンセプト

AI に画面を作らせるたびに色と余白が変わってしまう人に、値を先に固定する tokens.css 一式と、
トークンを経由しない生の色・px を洗い出す検査スクリプトを渡し、
**何度作り直しても同じ見た目から始まる状態**を手元に作る道具型商品。

productType: tool

## 価値軸（理想の未来の書き分け材料）

**「工程が減る」の一点に寄せない。** 前回の有料note（2026-08-11-notebooklm-deepresearch）は
価値軸が工程削減しかなく、letter-audit の A1 が
「理想の未来4か所がすべて同一文型に収束している」として2周連続で不合格になった。
その申し送り（`notes/2026-08-11-notebooklm-deepresearch/report.md`）に従い、
**書き分けられる軸を5つ定義してから**レターに渡す。

1. **再現**: 何度作り直しても同じ見た目から始まる。前回どう指示したかを思い出さなくてよい
2. **言語**: 直したい箇所を「なんか違う」ではなく `--space-4` `--color-accent` という値で指せる。
   AI への修正指示が1行になり、他人へのレビュー依頼も同じ語で通る
3. **持ち出し**: 次のプロジェクトに tokens.css を1枚置くだけで、同じ見た目が立ち上がる。
   案件ごとに作り直さない
4. **検査**: 破綻を自分の目で探さなくてよい。スクリプトが生の `#3b82f6` や `13px` を一覧にする。
   画面を全部開いて確認する作業が消える
5. **ダーク**: ライトとダークが同じファイルの中で対になっている。
   「あとでダーク対応する」という後工程が最初から無くなる

6. **見え方**: スクリーンショットをそのまま人に送れる。
   送る相手が見るのは、AI が選んだ色ではなく自分が決めた色である。
   見せる前に組み直す工程が予定から外れるのではなく、**見せられる状態が既定になる**

### 軸6を後から足した理由（letter-audit round 2 の指摘）

**1〜5は、名前は違っても全部「書き手の作業工程が減る」に帰着していた。**

- 1 再現 = 思い出さない
- 3 持ち出し = 選び直さない
- 4 検査 = 探さない
- 5 ダーク = やることが1つ消える

`letter-audit` round 2（15/16）はこれを A1 の不合格として検出した。

> 登録された5本の価値軸は、名前は違うが4本まで「書き手の作業工程が減る」という
> 同一の便益に帰着する。軸そのものが同じである以上、`sales-letter` に差し戻しても
> 言い回しを変えるだけで終わる公算が高い。

**`account.md` 112行の「人に見せたときに恥ずかしくないものを、毎回出せるようになりたい」が
一度も未来として描かれていなかった。** 減る作業の話しか書かれていないため、
支払い意欲「中〜高」の読者が払う理由に届いていない、という判定である。

軸6は**他者の目**の話であり、書き手の手間の話ではない。ここだけが減算ではなく到達である。

**この6つは互いに言い換えではない。** 1は時間、2は語彙、3は場所、4は視線、5は工程数、
**6は他者の目**の話であり、レターの4か所で違う未来を書ける。

**レターでは軸6を締めに置く。** 減る話で終わらせず、到達した状態で終わらせるためである。

## 渡すもの

- **形式**: CSS ファイル1本 ＋ Node スクリプト1本 ＋ 指示テンプレート2種 ＋ 作例HTML 3本

- **点数**:
  1. `tokens.css` 完全版1本（色 / タイポ / 余白 / 角丸 / 影の5系統。
     `:root` にライト、`@media (prefers-color-scheme: dark)` と `[data-theme="dark"]` にダーク）
  2. AI への渡し方テンプレート2種（プロジェクトのファイルとして @参照させる形 /
     チャットに貼り付けて渡す形）
  3. `check-tokens.mjs` 1本（生成された CSS・HTML を走査し、
     トークンを経由しない生の色コード・px 値・font-size を行番号付きで一覧にする）
  4. 作例3本（LP / 管理画面 / フォーム。すべて tokens.css だけで組んだ単一 HTML）

- **動作条件**: Node 18 以上（`check-tokens.mjs` の実行に必要。依存パッケージなし）。
  ブラウザは CSS カスタムプロパティが使えるもの。ビルドツール・フレームワーク不要。
  AI は Claude Code / Gemini / ChatGPT のいずれでもよいが、
  **ファイルを参照できる環境（Claude Code 等）のほうが効きが強い**ことを明記する。

- **最初の1歩**: `tokens.css` をプロジェクトの直下に置き、
  渡し方テンプレートAを AI に貼って、いま作りかけの画面を1つ作り直させる。
  そのあと `node check-tokens.mjs .` を1回叩く。

- **できないこと**:
  - 既存デザインの完全再現はしない（色は自分の値に差し替える前提である）
  - ブランド設計そのもの（何色にすべきか）は扱わない。**決め方ではなく固定の仕組みを渡す**
  - Figma との同期はしない
  - トークンを使わせても、レイアウトの良し悪しまでは決まらない

## 構成

### 無料部分（2000字）

症状から入る。**同じプロンプトで作り直したのに、前と色が違う**という場面を提示する。
そのうえで **色のトークンだけを完全公開する**（`--color-*` の全定義）。
`check-tokens.mjs` は出力例（検出結果のログ3行）だけを見せ、コードは有料部分に置く。
余白・タイポ・角丸・影のトークンは項目名だけ挙げて中身を出さない。

**1割を見せて9割を渡す比率を守る。** 色の定義は tokens.css 全体の約2割にあたるが、
ここを隠すと letter-audit の C2（再現性がなさそう）が落ちるため、あえて全文出す。

### 有料部分（5000〜8000字）

1. tokens.css 完全版（5系統すべて。ライト / ダークの対応まで）
2. なぜこの粒度で刻んだか（余白を4pxの倍数で8段にした理由。段を増やすと AI が迷う）
3. AI への渡し方テンプレートA（ファイル参照型）
4. AI への渡し方テンプレートB（貼り付け型）と、Bで落ちる箇所
5. check-tokens.mjs 全文と実行結果の読み方
6. 作例3本（LP / 管理画面 / フォーム）
7. 自分の色に差し替える手順
8. 動作条件・できないこと・つまずきどころ

## 対象読者

account.md のペルソナのうち、**すでに AI に画面を1つ以上作らせたことがあり、
かつ2回目以降を作った人**に絞る。

1回しか作っていない読者には「毎回違う」という症状が発生していないため、
本商品の価値が伝わらない。無料記事（月曜・金曜）で足りる。

コードを書ける必要はないが、**ファイルを1つ置いて Node を1回叩ける**ことは前提にする。

## pricing-strategy への申し送り

- **情報密度: 高。** 動く単位のコード（CSS 1本 + Node スクリプト1本 + 作例3本）を渡す。
  テキストテンプレートが中心だった前回の商品（情報密度「中」）より上である。
  読者の手元でそのまま実行でき、実行結果が目に見える。

- **想定価格帯の目安**: `market/2026-08-17.json` の価格中央値を必ず引用すること。
  ただし **UIデザインの有料率は4%** と低く、この領域で有料が成立している前例が薄い。
  情報密度は高いが、**天井は市場側の事情で抑えられる**。
  account.md の想定価格帯 980〜2,980円 の**下側〜中央**から入るのが妥当と考える。

- **天井の目安**: 「何度作り直しても同じ見た目から始まる状態を、1つのプロジェクトに作る」
  ところまで。案件横断のデザインシステム構築や、ブランドカラーの決定は天井の外である。
