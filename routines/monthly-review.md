# monthly-review

月次でボトルネックを診断し、実績を蓄積する Routine。

| 項目 | 設定 |
|---|---|
| cron | `0 8 1 * *`（月初 08:00 JST） |
| モデル | Sonnet 5 |
| effort | high |
| 消費 | 1/月 |

---

## 依存するスキル

| スキル | 状態 |
|---|---|
| `profile-accumulator` | **実装済み** |
| `revenue-maximizer` | **実装済み** |
| `scripts/note_market.py` | **実装済み**（`--update-profile` で note の実測値を書き込む） |
| `scripts/fetch-public.mjs` | 未実装（`data/metrics.json` が埋まらない） |

**下の「完成版」を登録する。** `data/` が空でも動く。
数値が無いときは「未測定」と書き、何を測れば分かるかを示す設計になっている。

> `data/metrics.json` が未取得でも、`research/market/{date}.json` に
> 自分のアカウントの実測値（記事数・フォロワー数・スキ中央値）が入っている。
> `revenue-maximizer` はそれを基準線として使える。

## プロンプト（旧・暫定版 — 参考として残す）

```
このリポジトリの先月の運用を振り返ってください。

まず CLAUDE.md を読み、ルールを守ってください。
特に「実績・体験・第三者の結果を創作しない」は絶対です。
data/ に実測値がなければ「まだ数値が無い」と書いてください。推測しないでください。

## 手順

1. notes/*/meta.json をすべて読み、先月分を集計する。
   - 本数（無料 / 有料）
   - カテゴリ別の内訳
   - 週ごとの推移

2. notes/*/report.md をすべて読み、以下を集計する。
   - 各ゲートの差し戻し回数
   - ethics-line が削除・修正した内容の傾向
   - 「書けなかったこと」として記録された主張の一覧

3. research/themes.md と knowledge/learnings.md を読む。
   - 在庫の残数
   - 範囲外として却下したテーマの傾向
   - 同じ範囲外テーマが繰り返し出ていないか

4. data/ に metrics.json があれば読む。無ければ「未取得」と記録する。

5. 気づいたことを整理し、Issue を1本立てる。

## 報告に必ず含めること

- 先月の本数と目標（週7本）との差
- **ethics-line が繰り返し検出した項目**
  → 同じ項目が何度も出るなら、writer への指示か voice.md を直すべき信号
- **「書けなかったこと」の一覧**
  → profile.md が埋まれば書けるようになるものが分かる
- **範囲外テーマの傾向**
  → 同じ領域が繰り返し高スコアで出るなら、カテゴリ設定を疑う
- 在庫の残数と、補充が追いついているか

## 書いてはいけないこと

- 収益・PV・フォロワー数の推測値
- 「順調です」「うまくいっています」といった評価
  → 事実と数字だけを書いてください
```

## プロンプト（完成版 — これを登録する）

```
このリポジトリの先月の運用を振り返り、実績を蓄積してください。

まず CLAUDE.md を読み、ルールを守ってください。
特に「実績・体験・第三者の結果を創作しない」は絶対です。
数値が無いときは「未測定」と書いてください。推測しないでください。

## 手順

1. 集計する。
   - notes/*/meta.json … 本数（無料/有料）、カテゴリ、タグ、週ごとの推移
   - notes/*/report.md … ゲートの差し戻し回数、ethics-line の検出内容、
                          「書けなかったこと」の一覧
   - research/themes.md … 在庫の残数
   - knowledge/learnings.md … 範囲外として却下したテーマの傾向

2. research/market/ の最新2ファイルを比較する。
   タグ別の需要÷供給が先月からどう動いたかを見る。
   自分のスキ中央値が市場水準に対してどこにいるかを出す。

   **JSON ではなく .md の要約表を読んでください。** 生データはコンテキストを
   汚します。数値の全量が必要なときだけ .json を開いてください。

3. profile-accumulator を実行する。
   data/ と notes/*/report.md から「言える実績」を profile.md に追記する。

   - 出所は必ず data/ か report.md か note の公開 API にする
   - すべての実績に「前提」を書く（どのジャンルで得た数値か）
   - <!-- AUTO:note-metrics --> ブロックの中は編集しない
     （note_market.py が上書きするため）
   - 「書けないこと」から項目を外すときは、1項目ずつ理由を添える

4. revenue-maximizer を実行する。
   顧客数 × 単価 × 購入回数 のうち、詰まっている1つを特定する。

   - 市場水準との「比」で判定する。絶対値だけで判断しない
   - 測定できない因数をボトルネックにしない
   - 次の1手は1つだけ出す。改善策を並べない
   - data/bottleneck.json に出力する

5. type: experience を解禁できるか判定する（profile-accumulator の判定に従う）。
   3条件すべてを満たすときだけ解禁する。
   - 同じジャンルの実績が実数値である
   - 天井を下げられる具体的な数字がある
   - 自分以外の結果が1つ以上ある（出典つき）

   揃っていなければ「まだ tool のみ」と報告してください。

6. Issue を1本立てて報告する。

## 報告に必ず含めること

- 先月の本数と目標（週7本）との差
- ボトルネックと次の1手（1つだけ）
- profile.md に追記した実績と、書かなかったこと
- ethics-line が繰り返し検出した項目
  → 同じ項目が何度も出るなら、writer への指示か voice.md を直すべき信号
- 範囲外テーマの傾向
  → 同じ領域が繰り返し高スコアで出るなら、カテゴリ設定を疑う
- 在庫の残数と、補充が追いついているか

## 書いてはいけないこと

- 収益・PV・フォロワー数の推測値
- 「順調です」「うまくいっています」といった評価
  → 事実と数字だけを書いてください
- 改善策の一覧
  → 次の1手を1つだけ書いてください。並べると何もやりません

## やってはいけないこと

- knowledge/account.md を書き換えないでください。
  カテゴリの変更が必要だと判断したら、判断材料を添えて報告するに留めます。
  在庫と過去記事を巻き込むため、人間が決めます。
```

---

## この Routine が最も重要な理由

**実績のない状態から始めて、運用そのものを実績に変換する。**

`profile-accumulator` が毎月 `profile.md` を育てる。数ヶ月後には
`type: experience` の有料noteを書ける材料が揃う。

それまでは `type: tool`（道具型）だけを作る。道具型は再現性の根拠を
成果物の検証可能性に置くため、実績がなくても成立する。
