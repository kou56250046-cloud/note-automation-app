3. **【到達・獲得】全員一致の枠が0件だったときに、「一番多い枠と、そこで空いていない人」まで画面と通知に出る。** 次の一手（誰に相談するか）が決まった状態で会議調整が終わる
4. 【減算】候補日を手作業で突き合わせる作業がなくなる

## 渡すもの

- **形式**: GAS コード（.gs）＋ HTML Service のテンプレート（.html）＋ プロンプト全文（Markdown）＋ 差し替え表（Markdown）
- **点数**:
  - GAS コード **4ファイル**（設定 `config.gs` / 入口 `intake.gs` / 中核と検証 `extract.gs` / 通知 `notify.gs`）
  - HTML Service **1画面**（`dashboard.html`。CSS・JS をインラインで自己完結。ヒートマップ）
  - プロンプト **1本**（曖昧語の解釈規則を含む）＋ `responseSchema` 定義 **1本**
  - 差し替え表 **1枚**（差し替え箇所 全6項目）
- **動作条件**:
  - Google アカウント（Google フォーム＋スプレッドシートが使えること）
  - Gemini API キー（スクリプトプロパティ `GEMINI_API_KEY` に登録）
  - Slack Incoming Webhook URL（**任意**。無くても画面と集計は動く）
  - Apps Script の実行権限を承認できること（外部 API を叩くため、シンプルトリガーでは動かない）
- **最初の1歩**: スクリプトプロパティに `GEMINI_API_KEY` を登録し、`config.gs` の `SHEET_NAME` を自分のシート名に変えて、フォームに1件テスト回答を入れる。E列に構造化された JSON が入ることを確認する
- **できないこと**:
  - **日付単位の日程調整には対応していない。** 曜日×時間帯の繰り返し枠（定例会議の枠決め）が対象である。「9月3日の14時」のような特定日を扱うにはシート構造から変える必要がある
  - **時間帯の粒度は午前・午後・夜の3枠が既定。** 1時間単位に割ることはできるが、枠数を増やすと Gemini の出力キーが増え、プロンプトの解釈規則も書き足す必要がある
  - **日本語以外の自由記述**は検証していない。プロンプトが日本語前提である
  - **Slack 以外の通知先**（メール / LINE / Chatwork）は含まない。`notify.gs` の POST 先を差し替える必要がある
  - **Google カレンダーの予定は見ない。** 参加者が書いた自由記述だけを根拠にする
  - **参加者が100人を超える規模**は想定していない。GAS の6分制限に当たる規模では分割実行が別途要る

## 構成

### 無料部分（`02-letter.md` / 2000字）

**出し惜しみしない。** 道具型で C2（再現性がなさそう）が落ちるのは中身を隠したときである。

見せる実物の断片:

- **プロンプトの曖昧語の解釈規則を3行だけ**（「いつでも」「夕方以降」「言及の無い曜日」の扱い。出力形式の指定と `responseSchema` は有料側）
- **差し替え表の6項目のうち3項目**（シート名 / 自由記述の列見出し / 時間帯の粒度）を、実際の記述例つきで
- **木曜と土曜の公開デモURL**（すでに無料で見られるヒートマップ画面をそのまま示す）
- **全員一致が0件だったときの通知文の実物1つ**

「1割を見せて9割を渡す」の比率に沿う。

### 有料部分（`03-draft.md` / 5000〜8000字）

1. 完成後の画面を先に見せる。何が手に入るかを最初に確定させる
2. 全体の流れと4ファイルの責務（どのファイルが何を持つか）
3. `config.gs` — 差し替え箇所を1ファイルに集約する設計と、その全文
4. `intake.gs` — フォーム受信・ヘッダー保証・後勝ちの上書き。全文
5. `extract.gs` — プロンプト全文・`responseSchema` 全文・Gemini 呼び出し・形式検証・再試行の全文
6. `notify.gs` — 締切トリガー・全員一致の枠の検出・0件時の代替提示・Slack POST の全文
7. `dashboard.html` — ヒートマップの全文（CSS・JS インライン。離散段階の配色と未回答の表現を含む）
8. **差し替え手順書** — 全6項目を、どのファイルの何行目を何に変えるかまで
9. 動かないときに最初に見る3箇所
10. できないことと、その回避方法

## 対象読者

`account.md` のペルソナを、この商品に合わせて絞ったもの。

**GAS で自動化を組める人で、定例会議や勉強会の日程調整だけは毎回チャットで聞いて回っている人。**

- コードは自分で書ける。書けないから買うのではない
- **自分で組むより速いと感じられなければ払わない**（`account.md`）
- 日程調整サービスを使わない、あるいは使えない事情がある（社外に情報を出せない、参加者にアカウントを作らせたくない）
- 「その仕組み使わせて」と言われたときに、渡す形になっていない

**外す読者**: 特定の日付で1回だけ調整したい人。この商品は繰り返し使う定例枠の決定が対象であり、単発の日程調整には既存サービスのほうが速い。

- **情報密度: 高**。理由は、コード4ファイル＋HTML1画面＋プロンプト＋`responseSchema`＋差し替え表という数えられる成果物を持ち、かつ月〜土の無料6本で各部品の設計思想を先に公開しているため、有料部分は「全部入り＋差し替え手順」に集中できること。説明で埋める必要がない
- **想定価格帯の目安**: `market/2026-08-29.md` の価格中央値は **500円**（有料率 11.5%）。`account.md` の想定価格帯は **1,480〜2,980円（中心1,480円）**。連載の完成版一式は単発記事とは商品が違うという理由で中央値の3倍を中心に置く方針が `account.md` に明記されている
- **前週（`2026-08-30-survey-kit`）と同価格帯にするかの判断が要る。** 成果物の点数は前週がコード5ファイル、今回は4ファイルで、HTML画面とプロンプトの点数は同じである。点数が1つ少ないことを理由に下げるか、ヒートマップ画面と0件時の代替提示という別の要素を理由に据え置くかを決めること
- **注意**: 実績がない状態である（`profile.md` の数値は旧ジャンル）。天井を上げる根拠は成果物の点数と動作条件だけであり、書き手の実績では上げられない
