# weekly-research

**このスキルが毎日投稿を成立させている。**

日次の記事生成は web 検索をしない。在庫（`research/themes.md`）から1本引くだけである。
その在庫をここで作る。

リサーチを日次で回すとトークンが尽きる（月2,000円相当）。週次に集約すると月250円になり、
**削減した1,750円がそのまま記事26本分の原資になる。**

---

## `researcher` サブエージェントで実行する

web 検索の結果でコンテキストが汚れるため `researcher` に委譲し、**要約と出典だけ**を受け取る。
スコアリングも `researcher` が行う（`analyst` は作らない）。

---

## 入力

| ファイル | 必須 | 何に使うか |
|---|:---:|---|
| `knowledge/account.md` | ○ | **書いてよい範囲**。主カテゴリ1＋サブ2〜3 |
| `knowledge/learnings.md` | ○ | 過去に却下したテーマ。同じものを拾い直さない |
| **`research/market/{最新}.md`** | — | **需要と供給の実測**。無ければ警告して続行する（止めない） |
| `research/themes.md` | — | 現在の在庫。無ければ新規作成 |
| `notes/*/meta.json` | — | 既出記事のタイトル。重複を避ける |

**`account.md` が無ければ停止し、`account-design` の実行を促す。** 範囲が決まっていない状態で
在庫を作ると、後から全部使えなくなる。

### market データを先に読む

`scripts/note_market.py` が日曜21時（JST）に実測し、`research/market/{date}.md` を出す。

**同じディレクトリの `.json` は読まない。** 20〜30行の要約表だけを読む。
生データを読むとコンテキストが汚れてトークンが跳ねる。Python が要約まで作り切っている。

そこにあるもの。

- タグ別の**需要**（人気上位のスキ中央値）と**供給**（新着の1日あたり投稿数）、その比
- タグ横断のクラスタ（テーマの塊）とスキ中央値
- 有料率と価格中央値
- 自分の位置（基準線）

**市場性の判断はここから取る。印象で決めない。**
初版は web 検索の印象で「空白地帯」を判断し、需要÷供給 0.064 の領域に突っ込んだ。
「調査範囲では見つからなかった」は、探し方の問題であって市場が空いている証拠ではない。

## まず在庫を数える

**第3版から、在庫は「1システム7本」を単位とする。**（`account.md` の連載構成）

```
pending の残数を数える
  ↓
7本そろっていて、かつ同じ連載（同じ systemId）なら → 補充せず終了
  ↓
そうでなければ → 1システムを選び、7本まとめて仕込む
```

**端数の補充をしない。** 連載は7本で1つのシステムを完成させるため、
3本だけ足すと週の構成が崩れる。**pending に7本未満の残りがあり、
それが前の連載の食べ残しなら `rejected` にして理由を `learnings.md` に書く。**

第2版までは「7本になるまで補充する」だった。単発記事を並べていたため
端数の補充が成立していた。**連載では成立しない。**

複数週分を先に仕込んでよいが、その場合も**7本単位**で、`systemId` を分ける。

## 調べること

`account.md` のサブカテゴリごとに、以下を探す。

| 探すもの | どこを見るか |
|---|---|
| **需要と供給** | **`market/{date}.md`**。ここが主。web 検索では分からない |
| 最近の変化 | 公式ドキュメントの更新、新機能、仕様変更 |
| 実物を出すための一次情報 | 公式ドキュメント、API リファレンス |

**web 検索は5件程度で切り上げる。** 需要の数値は market データが担うので、
検索は**一次情報の裏取り**だけに使う。

初版は15件検索していた。それは市場を知るためではなく、印象を作るための消費だった。

## スコアリング

**4軸で各5点。** `artifact` を足した。**根拠を必ず添える。** 点数だけでは後から検証できない。

| 軸 | 5点 | 1点 |
|---|---|---|
| **強み** | `account.md` の主カテゴリど真ん中。手元の材料だけで書ける | サブカテゴリの端。調べ直しが要る |
| **市場性** | `market` で需要÷供給が高いタグ・クラスタに属する | 需要÷供給が 0.1 未満。埋もれる |
| **支払い意欲** | 解決に金を払う痛みがある。時間かコストが直接減る | 知って終わり。行動が変わらない |
| **artifact** | プロンプト全文・コード全文・before/after を丸ごと出せる | 説明しかできない |

### artifact 軸を足した理由

**浅い記事はレビューでは直らない。テーマ選定の時点で決まっている。**

初版の1本目は「切り分け手順の説明」で、読者の手元に何も残らなかった。
その原因はテーマにあり、書き方にはなかった。

**`artifact` が2以下のテーマは在庫に入れない。** 合計スコアが高くても入れない。
これが浅い記事を上流で止める唯一の仕組みである。

### 市場性は数字を引用する

**推測を書かない。** `market/{date}.md` のタグ名かクラスタ番号と、その数値を引用する。

```
✕ market4: 需要が高そうで、競合が少ない領域である
○ market5: market/2026-08-06.md のタグ「GoogleAppsScript」は需要84 / 供給14.2件/日で
   比 5.91。クラスタ #8（Google / AI / GAS）はスキ中央値57.5。有料率13%と高い
```

引用元が書かれていないテーマは在庫に入れない。後から検証できないためである。

### 支払い意欲の判定

**これが `type: paid` の割り当てを決める。**

| 判定 | 特徴 |
|---|---|
| 高（4〜5） | 手順を丸ごと渡せる。テンプレート・コード・設計図の形になる |
| 中（3） | 考え方は有用だが、成果物として渡すものがない |
| 低（1〜2） | 情報を知れば終わり |

**支払い意欲4以上のテーマだけを `type: paid` に割り当てる。** 3以下を有料にすると
`letter-audit` の C4（高い、あとでいい）が通らない。

## カテゴリ範囲外の扱い

**スコアが高くても、`account.md` の範囲外なら在庫に入れない。**（CLAUDE.md ルール4）

note のアルゴリズムはアカウント単位で「この人は何の人か」を学習する。
カテゴリが散ると、その記事だけでなくアカウント全体の推薦が弱くなる。

**ただし捨てない。** `learnings.md` の「範囲外として在庫に入れなかったテーマ」に追記する。

```markdown
| 日付 | テーマ | スコア | 却下理由 |
|---|---|---|---|
| 2026-08-10 | ◯◯の始め方 | 12/15 | 主カテゴリの外（副業一般）。サブカテゴリにも該当なし |
```

**同じ範囲外テーマが繰り返し高スコアで出てくるなら、カテゴリ設定のほうを疑う信号である。**
四半期の棚卸しで `account-design` の見直しを検討する。

## 週の形 — 1システムを選び、7つに割る

**第3版から、7本を別々のテーマから引かない。**（`account.md` の連載構成）

```
1. その週のシステムを1つ選ぶ
2. 7分割する（下表の役割に沿う）
3. 各回の artifact を割り当てる
4. 日曜（完成版一式）の支払い意欲を判定する
```

### システムを選ぶ条件

| 条件 | 内容 |
|---|---|
| **規模** | GAS 200〜400行 / HTML Service 1画面 / 外部API 1〜2本 |
| **分割可能性** | 7回に割ったとき、**各回が単体で価値を持つ**か。1〜2点なら選ばない |
| 支払い意欲 | 完成版一式に4以上が付くか。**4未満のシステムは連載に選ばない** |
| 範囲 | `account.md` のサブカテゴリ①②③の**すべてを使える**か |

小さすぎると水増しになり、大きすぎると土曜までに終わらない。
**大きい題材は範囲を狭めて1週に収める。** 2週にまたがらせない。

### 7分割の既定

| 曜日 | 役割 | サブカテゴリ | 実物の既定 |
|---|---|---|---|
| 月 | 全体設計とデータの入口 | 2 | 設計図＋入口のコード全文 |
| 火 | 中核処理（Gemini 呼び出し・変換） | 3 | プロンプト全文＋呼び出しコード |
| 水 | 失敗時の扱い（リトライ・冪等性） | 2 | 壊れるコード → 直したコード |
| 木 | **画面を付ける（HTML Service）** | 1 | before/after デモ＋HTML全文 |
| 金 | トリガーと運用（権限・制限・通知） | 2 | トリガー設定＋通知コード全文 |
| 土 | つまずきポイント集 | 1 | before → after を3件以上 |
| 日 | **完成版一式＋差し替え手順書（paid）** | 3 | 全コード＋差し替え表 |

### 割り当てのルール

1. **paid（日曜）は連載の完成版である。** 支払い意欲4以上を確認する。
   4未満ならそのシステムを連載に選ばない。**支払い意欲3以下を有料にしない**
2. **各記事は単体で完結させる。** `angle` に「単体で読めるようにする前提の3行要約」を書く
3. **木曜と土曜は必ずサブ①にする。** UIデザイン（需要÷供給 5.767・1位）タグを
   毎週使うための条件である。ここを外すと最大の空白を使わない週ができる
4. **日曜の `productTypeHint` を必ず書く。** 第3版では原則 `tool`（道具型）。
   書かれていないと `product-concept` が停止する
5. 7本すべてに同じ `systemId` を付ける。`/note-week` が連載であることを判定する

### 有料テーマには「減算ではない価値軸」を1本添える

**過去2件の商品が、同じ理由で `letter-audit` の A1 を落としている。**

価値軸が全部「書き手の作業工程が減る」に帰着すると、理想の未来が
「〜がなくなる／要らない」の否定形に収束して通らない。

`type: paid` のテーマには、`angle` に**到達・獲得の軸を最低1つ**書き添える。
例:「スクリーンショットをそのまま人に送れる状態になる」。

### 実行はすべてローカルである

生成は日曜の `/note-week` が一括で行う。**Routines は廃止した。**
`type: paid` のテーマに「ローカルで実行」と書き添える必要はもう無い。

## 重複チェック

以下と重ならないことを確認する。

| 対象 | 見るもの |
|---|---|
| 既出記事 | `notes/*/meta.json` のタイトルとカテゴリ |
| 在庫 | `research/themes.md` の `status: pending` |
| 却下済み | `learnings.md` の両テーブル |

**ここでの判定は粗くてよい。** 最終的には `scripts/dedup.py` が TF-IDF で機械判定する。
明らかに同じテーマだけを弾く。

### 必ず書くこと

| フィールド | なぜ必要か |
|---|---|
| `rationale` | **次点と落とした理由を含める。** market の数値引用を必ず入れる |
| **`artifactPlan`** | **何を実物として出すか。** これが書けないテーマは在庫に入れない |
| **`hashtags`** | `account.md` の既定に従う。空白タグを主軸に、大きいタグは1つまで |
| `angle` | 既出記事との差別化点。`dedup.py` で弾かれないため |
| `sources` | 出典。記事執筆時に参照する |
| `productTypeHint` | `type: paid` のみ。道具型か体験談型かの申し送り |

**`profile.md` が空のうちは `productTypeHint: tool` 以外を書かない。**
体験談型は実績が必須であり、`sales-letter` が停止する。

## やらないこと

- **記事を書かない。**
- **7本を無条件に足さない。** 7本になるまで補充する
- **範囲外テーマを在庫に入れない。** スコアが高くても入れない
- **`artifact` が2以下のテーマを入れない。** 合計スコアが高くても入れない
- **`rationale` を省略しない。** 選定理由が残らないと改善できない
- **出典のないテーマを入れない。**
- **market の数値を引用せずに市場性を書かない。** 印象で決めた瞬間に初版の失敗を繰り返す
- **web 検索を5件を超えて回さない。** 需要の判断は market データの担当である

---

## 在庫が切れると止まる

**毎日投稿の唯一の停止要因は在庫の枯渇である。**

`stock-alert` Actions が毎朝チェックし、`pending` が3本未満なら Issue を立てる。
Issue が立ったら、日曜を待たずにこのスキルを実行する。

**在庫が空の状態で記事を書かない。** 空の在庫を埋めるために、その場でテーマを作らない。
