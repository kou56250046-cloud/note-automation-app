スキルが起動しないとき、多くの人はまず frontmatter を疑います。

私も同じ順番で詰まりました。

結論から言うと、**frontmatter は3番目に見る場所**です。

先に見るべき場所が2つあります。


## frontmatterを3回書き直しても直らない理由

「動くようにはなったが、思ったスキルが呼ばれない」

この状態でまず手が伸びるのは、frontmatter の書き直しです。

インデントを揃え直し、キーの表記を見直し、それでも呼ばれない。

もう一度直す。それでも呼ばれない。

同じ設定を3回書き直して、まだ動いていない。

この状態になっているなら、原因は frontmatter の中身ではなく、
**frontmatter がそもそも読まれる位置にあるか**、
**別の経路で止まっているか**のどちらかです。

順番に確認していきます。


## 手順1: description の「読まれ方」を疑う

frontmatter の中で、起動判定に使われるのは主に `description` です。

ここが曖昧だと、構文が正しくてもスキルは呼ばれません。

このリポジトリの `.claude/skills/editorial/ethics-line/SKILL.md` を開くと、
description は次のように書かれています。

```
description: 記事に「偽の限定」「盛った恐怖」「裏付けのない体験談」「書きっぱなしの弱点」「収益の断定表現」が混入していないかを検出し、無条件で修正させるスキル。ユーザーが「煽りすぎていないか見て」「法的に問題ないか確認して」「この表現は大丈夫か」と言ったとき、また note-factory のフローで無料記事の 01-draft.md または有料noteの 02-letter.md が出力された直後に必ず実行すること。
```

含まれている要素は3つです。

- 何を検出するか（偽の限定、盛った恐怖、など具体名を列挙）
- ユーザーがどう言ったときに呼ぶか（発話をそのまま「」で並べる）
- どのファイルが出力された直後に呼ぶか（01-draft.md、02-letter.md）

「便利な処理をするスキルです」という description には、この3つがありません。

何を検出するかも、ユーザーがどう言ったときかも書かれていないため、
Claude 側は呼ぶタイミングを判断する材料を持てません。

自分のスキルの description に、この3要素が入っているかを確認します。

直らないなら、次の手順に進みます。


## 手順2: 呼び出しの経路を疑う

frontmatter の中身が正しくても、呼ばれない場合があります。

**置き場所と、モデル指定の場所がずれている**ケースです。

まず置き場所です。このリポジトリでスキルは以下の形で置かれています。

```
.claude/skills/research/account-design/SKILL.md
.claude/skills/editorial/ethics-line/SKILL.md
```

`.claude/skills/{分類}/{名前}/SKILL.md` という2階層です。

分類は `research` か `editorial` のどちらかです。

一方、スラッシュコマンドは同じ `.claude/` 配下でも置き場所が違います。

```
.claude/commands/note-daily.md
```

サブディレクトリも `SKILL.md` も持たず、`.claude/commands/` 直下にファイル1本を置くだけです。

スキルのつもりで `.claude/commands/` に置いていないか。

逆にコマンドのつもりで `.claude/skills/` に置いていないか。

実行しているプロジェクトの直下に、この `.claude/` があるかも合わせて確認します。

次にモデル指定です。

`model: opus` のような指定は、`.claude/agents/critic.md` のようなエージェント定義のフロントマターにあります。

```
---
name: critic
description: レターと本文を読者の目で判定するエージェント。有料noteの letter-audit と無料記事の reader-feedback で使う。親のコンテキストを渡してはならない。
tools: Read, Write
model: opus
---
```

`.claude/skills/*/SKILL.md` には、この `model` フィールド自体がありません。

スキルを Task ツールでサブエージェントとして呼んだときだけ、
呼び出し先のエージェント定義の `model` が反映されます。

会話の中でスキルの説明文だけを読み込ませた場合、
このエージェント定義を経由しないため、指定は反映されません。

一度、スラッシュコマンド（例: `/note-daily`）として直接呼んで、
動くかどうかだけを確認してください。

それで動くなら、原因は frontmatter ではなく呼び出し経路です。


## 手順3: サブエージェントのセッション状態を疑う

手順1、手順2で直らない場合、最後に見るのがここです。

サブエージェントとして呼ばれるスキルには、セッションの上限があります。

会話が長く続いた状態でスキルを呼ぶと、
その時点までのやり取りが積み上がっていて、
スキルの定義が期待どおりに読み込まれないことがあります。

切り分け方は次の手順です。

- 新しい会話を開く
- 手順2で確認したスラッシュコマンドを、同じ書き方でもう一度呼ぶ
- 新しい会話で呼んで動くなら、原因はセッション側だったと判断できます
- 新しい会話でも同じように動かないなら、原因はセッションではありません

セッションでないなら、手順1の description か、
手順2の置き場所・呼び出し経路に戻って見直します。


## つまずきどころ

この3手順を試すとき、つまずきやすい点が2つあります。

1つ目は、手順を戻ってしまうことです。

手順2で直らないと、つい手順1の description に戻って直したくなります。

同じ場所を往復すると、どこまで確認したか分からなくなります。

1つずつ、順番に進めてください。

2つ目は、複数の原因が重なっているケースです。

description が曖昧で、かつ呼び出し経路もずれている、ということがあります。

この場合、手順1を直しただけでは動きません。

3手順すべてを一通り確認してから、判断してください。


## 今日やること

まず、今動いていないスキルを1つ選んでください。

そのスキルを、**スラッシュコマンドとして直接呼んでみます。**

それで動くなら、原因は frontmatter ではなく呼び出し経路にあります。

それでも動かないなら、新しい会話を開いて、もう一度同じスキルを呼んでください。

この2つの切り分けだけで、直すべき場所がどこか分かります。


frontmatter を書き直す前に、まずこの2つを試してください。

順番を変えるだけで、直すべき場所が見えてきます。
