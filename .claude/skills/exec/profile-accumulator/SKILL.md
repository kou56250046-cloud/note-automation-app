# profile-accumulator

**`profile.md` は「書いてよいことの上限」を決めるファイルである。**

ここに無い実績・数字・体験は記事に書けない（CLAUDE.md ルール3）。
このスキルはその上限を、**実測にもとづいてだけ**広げる。

---

## 最も重要なこと

**創作しない。** 足りないものを埋めるために書かない。

書いてよいのは次の3つだけである。

| 種別 | 出所 |
|---|---|
| 実績（数値） | `data/*.json` / `notes/*/report.md` / note の公開 API |
| 体験（エピソード） | 実際の運用ログ。`report.md` に記録があるもの |
| 第三者の結果 | **出典URL、または許諾を得た旨。架空の「読者の声」を作らない** |

**判断に迷ったら書かない。** 書かなかったことは `report` に残す。
`profile.md` が空のままでも無料記事と道具型の有料noteは成立する。

---

## `note_market.py` と棲み分ける

`profile.md` の実績欄には、自動更新されるブロックがある。

```markdown
<!-- AUTO:note-metrics -->
（scripts/note_market.py が毎週上書きする）
<!-- /AUTO:note-metrics -->
```

**このブロックの中を手で編集しない。** 次回の実行で上書きされる。

| 担当 | 何を書くか |
|---|---|
| `note_market.py --update-profile` | note の公開データ（記事数・フォロワー数・スキ中央値） |
| **このスキル** | **それ以外**（販売実績・運用ログ由来の事実・第三者の結果・体験） |

AUTO ブロックの**外側**に追記する。

---

## 入力

| ファイル | 必須 | 何に使うか |
|---|:---:|---|
| `knowledge/profile.md` | ○ | 現在の実績と「書けないこと」 |
| `notes/*/report.md` | ○ | 運用ログ。ゲートの通過状況、書けなかったこと |
| `notes/*/meta.json` | ○ | 記事数・カテゴリ・公開日 |
| `data/metrics.json` | — | 数値。無ければ「未取得」と記録する |
| `data/revenue.json` | — | 販売実績。無ければ「販売実績なし」と記録する |
| `research/market/{最新}.json` | — | 市場の水準。自分の位置づけに使う |

**`data/` が空でも停止しない。** 「まだ数値が無い」と書けばよい。
無いことを無いと書くのが、このスキルの正しい振る舞いである。

---

## 1. 実績を追記する

### 書式（`profile.md` の形式に従う）

```markdown
### YYYY-MM-DD 何を達成したか

- 数値: 具体的な値
- 出所: data/revenue.json / notes/{slug}/report.md など
- 期間: いつからいつまで
- 前提: 再現に必要な条件（これがないと読者が誤解する）
```

### 「前提」を省かない

**数値そのものは事実でも、条件を落とすと事実でなくなる。**

```
✕ 「フォロワー83人」
    → どのジャンルで得たか分からない。AI技術記事の実績と誤読される

○ 「フォロワー83人（2026年4〜5月の日常・脳科学ジャンル26本での数値。
    AI技術ジャンルの実績ではない）」
```

前提を落とした引用は `ethics-line` の E3 に当たる。
**追記する時点で前提を書いておかないと、`writer` が落として使う。**

---

## 2. 「書けないこと」から項目を外す

`profile.md` の「書けないこと」は、実績が貯まるたびに短くなる。
**ただし外す条件は厳しい。**

| 外してよい | 外してはいけない |
|---|---|
| 実測値がその項目を**直接**カバーしている | 近い数値があるだけ |
| 同じジャンル・同じ文脈で得た数値である | 別ジャンルの数値で代用しようとしている |
| 出所が `data/` か公開 API にある | 記憶や推測にもとづく |

### 判定例

```
項目: 「読者数・フォロワー数・PV（アカウント開設前）」

  note_market.py がフォロワー83人を実測した
    → 「アカウント開設前」という前提は消えた
    → **条件つきで外してよい。** ただし文言を書き換える:
       「AI技術ジャンルでのフォロワー数・読者数（旧ジャンルの数値は使えない）」

項目: 「収益額・売上（まだ売上がない）」

  data/revenue.json が無い
    → **外さない。** 売上が発生するまで維持する
```

**外すときは1項目ずつ、理由を添えて報告する。** まとめて消さない。

---

## 3. `experience` 型を解禁するか判定する

**道具型（`tool`）だけで運用している状態から、体験談型を解禁するかの判断。**

3つすべてを満たすときだけ解禁する。

| # | 条件 | 確認方法 |
|---|---|---|
| 1 | **同じジャンル**の実績が実数値である | `profile.md` の実績欄。旧ジャンルの数値は数えない |
| 2 | **天井を下げられる**具体的な数字がある | 「月◯円」「◯日で」など、読者が届くと感じる範囲 |
| 3 | **自分以外の結果**が1つ以上ある（出典つき） | 購入者の報告。**架空の声を作らない** |

**1つでも欠けたら `tool` のままにする。**

体験談型を選んで実績が足りないと、`letter-audit` の C2 と
`ethics-line` の E3 で必ず止まる。時間の無駄になる。

解禁したら `knowledge/account.md` と `CLAUDE.md`「商品の型」に反映する。

---

## 4. 体験を記録する

「自分がダメだった頃」のエピソード。`type: experience` の再現性④に使う。

**抽象的な述懐ではなく、いつ・何をして・どうなったかを書く。**

```
✕ 「最初は苦労しました」
○ 「2026-08-06、スキルが起動せず frontmatter を3回書き直した。
    原因は description の書き方だった（notes/2026-08-06-.../report.md）」
```

**運用ログに記録があるものだけを書く。** 記憶で補わない。

---

## 出力

### `knowledge/profile.md` への追記

AUTO ブロックの外側。日付の新しい順に並べる。

### 報告

```
profile.md を更新しました

追記した実績: 1件
  - 2026-09-01 有料note初回販売（data/revenue.json）

「書けないこと」から外した項目: 1件
  - 「読者数・フォロワー数」→ 文言を変更
    理由: note_market.py がフォロワー83人を実測した。ただし旧ジャンルの
    数値なので「AI技術ジャンルでの」という限定を付けて残した

experience の解禁: しない
  理由: 条件3（自分以外の結果）が0件。購入者の報告が無い

書かなかったこと: 2件
  - 「作業時間が半分になった」— 計測していない。data/ に根拠が無い
  - 「読者から好評だった」— 出典が無い
```

## 物差し（これを満たさなければ書き込まない）

| # | 条件 | 満たさないとき |
|---|---|---|
| 1 | すべての数値に出所が書かれている | 書かない |
| 2 | すべての実績に前提が書かれている | 前提を書く。省かない |
| 3 | 別ジャンルの数値を無条件に流用していない | 限定を付ける |
| 4 | 第三者の結果に出典URLか許諾の記録がある | 書かない |
| 5 | AUTO ブロックの中を編集していない | 外側に移す |
| 6 | 「書けないこと」を外した理由が1項目ずつ書かれている | 理由を書く |
| 7 | `experience` 解禁の3条件をすべて確認している | `tool` のままにする |

**迷ったら書かない。** 書かなかったことを報告するほうが、
書きすぎて `ethics-line` に差し戻されるより安い。

---

## やらないこと

- **記事を書かない。**
- **数値を推定しない。** 「おそらく◯件」を書かない
- **架空の購入者・読者を作らない**
- **AUTO ブロックを手で編集しない**
- **まとめて「書けないこと」を消さない。** 1項目ずつ判断する
- **良し悪しを評価しない。** 事実を積むだけである
