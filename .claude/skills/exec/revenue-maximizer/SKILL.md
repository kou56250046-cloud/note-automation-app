# revenue-maximizer

**売上 = 顧客数 × 単価 × 購入回数**

3つのうち**最も詰まっている1つ**を特定する。それだけがこのスキルの仕事である。

---

## 改善策を並べない

**5個の施策を出すと、人はどれもやらない。**

このスキルの出力は「次にやる1手」である。順位をつけた一覧ではない。

```
✕ 「①タイトルを改善 ②価格を見直し ③投稿頻度を上げ ④タグを変更 ⑤…」
    → 何もやらない結果になる

○ 「ボトルネックは顧客数。次の1手は投稿タグを空白タグへ寄せること」
    → 1つだけ。今週やれる
```

---

## 入力

| ファイル | 必須 | 何に使うか |
|---|:---:|---|
| `notes/*/meta.json` | ○ | 記事数・カテゴリ・タグ・公開日 |
| `notes/*/report.md` | ○ | ゲートの通過状況。生産の詰まり |
| `research/market/{最新}.json` | ○ | **市場の水準。自分の位置を相対で見る** |
| `data/metrics.json` | — | PV・スキ・フォロワー推移。無ければ「未取得」 |
| `data/revenue.json` | — | 販売数・売上。無ければ「販売実績なし」 |
| `knowledge/profile.md` | — | 実績 |

**`data/` が空でも停止しない。** 数値が無いときの振る舞いは後述する。

---

## 1. 3因数を分解する

| 因数 | 何で測るか | 詰まりの症状 |
|---|---|---|
| **顧客数** | 記事のスキ数・フォロワー増加・有料noteの閲覧数 | 読まれていない。届いていない |
| **単価** | 販売価格 × 市場中央値との比 | 安すぎる。または高くて売れない |
| **購入回数** | 同じ人が2本目を買うか | 1本で終わっている。次が無い |

### 市場と比べる（絶対値で見ない）

`market/{date}.json` に自分の位置を測る基準がある。

```
自分のスキ中央値        7
市場の人気記事の中央値  62
  → 顧客数の因数が市場水準の 1/9。ここが詰まっている

自分の価格             1,480円
市場の価格中央値         800円
  → 単価は市場の1.85倍。ここは詰まっていない
```

**絶対値だけを見て「少ない」と判断しない。** 市場水準との比で見る。

---

## 2. ボトルネックを1つに絞る

**3つとも改善しようとしない。** 最も比率の低い1つを選ぶ。

```
顧客数  市場比 0.11  ← 最も低い。ここがボトルネック
単価    市場比 1.85
購入回数 測定不能（販売実績なし）
```

### 順序の原則

**測定できない因数をボトルネックにしない。**

販売実績が0のときに「購入回数が課題」と言っても、打ち手が無い。
測定できる因数のうち最も低いものを選ぶ。

### 段階の原則

**顧客数が市場水準に届いていないうちは、単価と購入回数を触らない。**

読まれていない状態で価格を上げ下げしても、母数が小さすぎて結果が分からない。
**順番は 顧客数 → 単価 → 購入回数 である。**

---

## 3. 次の1手を決める

ボトルネックごとに、打ち手の候補は決まっている。**その中から1つだけ選ぶ。**

### 顧客数が詰まっているとき

| 打ち手 | 判断材料 |
|---|---|
| **投稿タグを空白タグへ寄せる** | `market` の需要÷供給。0.1未満のタグを使っていないか |
| テーマを需要の高いクラスタへ寄せる | `market` のクラスタ別スキ中央値 |
| 実物の強度を上げる | `report.md` で `artifacts` が1種類しかない記事が続いていないか |
| 投稿の継続性 | 週7本を維持できているか。在庫切れで止まっていないか |

> **最初に疑うのはタグである。** 需要÷供給が2桁違うので、
> 同じ記事でもタグを変えるだけで到達が変わる。

### 単価が詰まっているとき

| 打ち手 | 判断材料 |
|---|---|
| 情報密度を上げて値上げする | `pricing-strategy` の密度判定。渡すものを増やす |
| 天井を下げて価格も下げる | `letter-audit` の C4 が繰り返し×なら、価格と中身が釣り合っていない |

**値下げで解決しようとしない。** 安いほど再現性の不安が増える（`letter-audit` C4）。

### 購入回数が詰まっているとき

| 打ち手 | 判断材料 |
|---|---|
| 2本目を作る | 1本目の購入者が次に困ることは何か |
| 商品同士を繋げる | 前の商品の「できないこと」が次の商品になっていないか |

---

## 4. 数値が無いときの振る舞い

**推測しない。何を測れば分かるかを示す。**

```
✕ 「おそらく顧客数がボトルネックです」
    → 根拠が無い。判断ではなく感想

○ 「販売実績が data/revenue.json に無いため、単価と購入回数は判定できません。
    測定できる顧客数だけで見ると、スキ中央値7に対し市場の人気記事は62で
    市場比 0.11 です。まず顧客数から着手します。

    単価の判定には有料note1本の販売数が要ります。
    次に有料noteを出したら data/revenue.json に記録してください。」
```

**「測れないから分からない」と書くことは、このスキルの失敗ではない。**
測れないのに断定するほうが失敗である。

## 出力

### `data/bottleneck.json`

```json
{
  "date": "2026-09-01",
  "bottleneck": "customers",
  "factors": {
    "customers": { "value": 7, "marketBaseline": 62, "ratio": 0.11, "measurable": true },
    "price": { "value": 1480, "marketBaseline": 800, "ratio": 1.85, "measurable": true },
    "repeat": { "value": null, "marketBaseline": null, "ratio": null, "measurable": false }
  },
  "nextAction": "投稿タグを空白タグ（Webデザイン / GAS / NotebookLM）へ寄せる",
  "rationale": "market/2026-08-07.json で ClaudeCode の需要÷供給が 0.069、生成AI が 0.043。直近5本がこの2タグを主軸にしていた。Webデザイン(7.80) / NotebookLM(6.28) へ寄せる",
  "notMeasurable": ["repeat"],
  "toMeasure": "有料note1本の販売数を data/revenue.json に記録する",
  "source": "research/market/2026-08-07.json"
}
```

### 報告

```
ボトルネック: 顧客数（市場比 0.11）

  スキ中央値 7 に対し、市場の人気記事は 62。

次の1手: 投稿タグを空白タグへ寄せる

  直近5本が ClaudeCode（需要÷供給 0.069）と生成AI（0.043）を
  主軸にしていました。1日400件以上に押し流される場所です。
  Webデザイン(7.80) / NotebookLM(6.28) へ寄せます。

判定できなかったもの: 購入回数
  販売実績が data/revenue.json にありません。
  有料noteを1本出したら記録してください。

触らないもの: 単価
  市場比 1.85 で詰まっていません。顧客数が市場水準に届くまで動かしません。
```

## 物差し（これを満たさなければ出力しない）

| # | 条件 | 満たさないとき |
|---|---|---|
| 1 | ボトルネックが**1つ**に特定されている | 絞る。2つ挙げない |
| 2 | 市場水準との**比**で判定している | 絶対値だけで判断しない |
| 3 | 測定できない因数をボトルネックにしていない | 測定できるものから選ぶ |
| 4 | 次の1手が**1つ**である | 1つに絞る |
| 5 | 次の1手に `market` の数値が引用されている | 印象で決めない |
| 6 | 顧客数が未達のまま単価・購入回数を触っていない | 順序を守る |
| 7 | 数値が無い項目を「未測定」と明記している | 推測を書かない |

---

## やらないこと

- **改善策を並べない。** 1手だけ出す
- **推測で数値を作らない**
- **記事を書かない。** テーマの反映は `weekly-research` の担当である
- **`account.md` を書き換えない。** カテゴリの変更は `account-design` の担当である
- **値下げを最初の打ち手にしない**

> **カテゴリごと変えるべきだと判断したときは、実行せずに報告する。**
> `account-design` の見直しは影響範囲が大きく、在庫と過去記事を巻き込む。
> 判断材料（範囲外テーマの頻度、需要÷供給の推移）を添えて人間に回す。
