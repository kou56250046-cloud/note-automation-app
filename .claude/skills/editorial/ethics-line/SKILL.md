# ethics-line

**このゲートだけは回数制限がない。検出ゼロになるまで通さない。**

`letter-audit` と `reader-feedback` は「売れるか」を見る。このスキルは「やってはいけないことをしていないか」を見る。目的が違うので、同じエージェントに兼務させない。**必ず `auditor` サブエージェントで実行し、売るための文脈を一切渡さない。**

売る文脈を知っているエージェントは、効果のある表現を守ろうとして線引きが甘くなる。

---

## モード — 対象で検出項目が変わる

**このスキルは無料記事と有料noteの両方で実行する。** ただし検出項目が変わる。

| モード | 対象 | 検出項目 | 上限 |
|---|---|---|---|
| `full` | 有料note | **E1〜E5 の全5項目** | なし |
| `light` | **無料記事** | **E3・E5 の2項目のみ** | なし |

### なぜ無料記事で2項目に絞るのか

無料記事は**売らない**。したがって以下が構造的に発生しない。

- **E1（偽の限定）** — 販売しないので期限も値上げも特典終了も存在しない
- **E2（盛った恐怖）** — 購買を促す恐怖の設計そのものがない
- **E4（書きっぱなしの弱点）** — 商品の弱点を書く場面がない

### なぜ E3 と E5 は外さないのか

**実績のないアカウントほど、この2つは混入しやすいからである。**

| 項目 | 無料記事で起きること |
|---|---|
| **E3 裏付けのない実績** | 記事に説得力を持たせようとして「◯人が使っている」「効果が確認されている」と書いてしまう |
| **E5 断定表現** | 「必ず」「誰でも」「絶対に」で言い切ってしまう |

無料でも景品表示法の対象になる。**無料だから緩めてよい、ということはない。**

**どちらのモードでも回数制限は設けない。** 検出ゼロになるまで通さない。

---

## 前提の線引き

**焦らせる演出そのものはグレーではない。白である。** アウトなのは嘘だけ。

- 本物の期限を明記する → 白
- 実際に値上げする予定を書く → 白
- 3日間限定と書いて延長する → **アウト**
- 値上げすると書いて上げない → **アウト**

この区別を曖昧にして全部を削らせない。**削るのは嘘だけ。**

---

## 入力

**`meta.json` の `type` を最初に読み、モードを決める。**

| `type` | モード | 読むファイル |
|---|---|---|
| `free` | `light` | `notes/{slug}/01-draft.md`<br>`knowledge/profile.md` |
| `paid` | `full` | `notes/{slug}/02-letter.md`<br>`notes/{slug}/03-draft.md`<br>`notes/{slug}/letter-meta.json` の `deadlineClaims`<br>`knowledge/profile.md` |

`knowledge/profile.md` はどちらのモードでも必ず読む。**「書けないこと」セクションが E3 の判定基準そのものである。**

> **`03-draft.md` は追跡されていない（`.gitignore` 対象）。** ローカル実行時にのみ存在する。
> クラウドで有料noteを検査しようとしてファイルが無い場合は、停止して報告する。推測で通さない。

---

## 出力

- `notes/{slug}/ethics.json`

```json
{
  "clear": false,
  "mode": "light",
  "checkedItems": ["E3", "E5"],
  "rounds": 1,
  "findings": [
    {
      "id": "E3",
      "severity": "block",
      "lines": [42],
      "quote": "多くの人がこの方法で成果を出しています",
      "why": "profile.md の「書けないこと」に『◯人が使っているといった利用者数』が列挙されている。母数の根拠がなく、景品表示法の優良誤認にあたるおそれ",
      "fix": "削除する。人数を主張せず、手順そのものの説明に置き換える"
    }
  ]
}
```

**`mode` と `checkedItems` を必ず出力する。** どの範囲を検査したかが後から検証できなくなる。
`light` で `clear: true` が出ても、それは E1・E2・E4 を検査した結果ではない。

`severity` は2種類だけ。**中間評価は作らない。**

- `block` — 明らかな地雷。**必ず自動修正する。** これが1つでも残れば `clear: false`
- `review` — 判断に迷った表現。**自動修正せず人間に回す。** `clear` の判定には影響させない

迷ったものを勝手に消さないための区別である。判断基準は「嘘だと断定できるか」。断定できれば `block`、できなければ `review`。

## 検出項目

| ID | 項目 | `full`（有料note） | `light`（無料記事） |
|---|---|:---:|:---:|
| E1 | 偽の限定 | ○ | — |
| E2 | 盛った恐怖 | ○ | — |
| **E3** | **裏付けのない実績・体験談** | **○** | **○** |
| E4 | 書きっぱなしの弱点 | ○ | — |
| **E5** | **医療・投資・収益の断定表現** | **○** | **○** |

### E1. 偽の限定

`letter-meta.json` の `deadlineClaims` を1つずつ検証する。

| 記述の型 | 通す条件 |
|---|---|
| 「◯日間限定」 | 終了日が具体的に決まっていること |
| 「◯部で終了」 | 部数が決まっていて、到達時に実際に止めること |
| 「◯日から値上げ」 | 値上げ後の価格と実施日が決まっていること |
| 「先着特典」 | 特典の中身と人数が決まっていること |

**決まっていないものは削除させる。** 「後で決める」は通さない。

### E2. 盛った恐怖

- 恐怖が2つ以上ある → 1つに減らす
- 「もう手遅れ」に相当する記述がある → 回避可能な位置まで戻す
- 恐怖の描写が本人の体験に紐づいていない → 削除する

**E2の判定基準:** `profile.md` に記載のない地獄を描いていたら×。自分が体験していない地獄は、読者に伝わる前に嘘っぽさが伝わる。

### E3. 裏付けのない実績・体験談

**両モードで検査する。実績のないアカウントで最も混入しやすい項目である。**

**判定基準は `profile.md` の「書けないこと」セクションである。** ここに列挙された主張は、
言い換えても書いてはならない。

- `profile.md` に無い数字が書かれている → 削除または修正
- 他人の結果を引用しているが出典が無い → 出典を書くか削除
- 「多くの人が」「みんな」など、母数のない一般化 → 具体化するか削除
- 「実績があります」と匂わせているが根拠がない → 削除

**架空の第三者の声を作らせない。** これは検出したら即座に削除。

#### 誤検出を避ける線引き

**数値や成果を伴わない作業上の描写は E3 ではない。**

道具型（`productType: tool`）のレターには「この道具がなかったとき何が面倒だったか」を書くブロックがある。
これは体験の描写ではあるが、成果の主張ではない。

| ✕ E3 として検出する | ○ 検出しない |
|---|---|
| 「これで月◯万円になった」 | 「毎回手でコピペしていた」 |
| 「作業時間が◯%減った」 | 「同じ設定を3回書き直した」 |
| 「◯人が使っている」 | 「どこに何を書いたか忘れた」 |
| 「効果が確認されている」 | 「バージョンがずれて動かなくなった」 |

**数値・割合・人数・効果の主張が含まれるかどうか**で切り分ける。
作業の面倒さを描写しただけの文を削らせると、道具型のレターが書けなくなる。

### E4. 書きっぱなしの弱点

「これはできません」と正直に書くのは正解である。ただし**書きっぱなしにすると、それが買わない理由として残る。**

- 弱点・できないことの記述を検出する
- その直後に「その代わりこうしました」に相当する補完があるか確認する
- 無ければ補完を追加させる

**これは削除ではなく追加で直す項目。** 正直さを削らせない。

### E5. 医療・投資・収益の断定表現

- 「必ず稼げる」「確実に」「誰でも100%」 → 削除
- 収益の保証に読める表現 → 「私の場合は」に限定させる
- 健康・医療に関する効果の断定 → 削除

---

## 動作

```
1. meta.json の type を読み、モードを決める
     type: free → light（E3・E5 のみ）
     type: paid → full （E1〜E5）
2. 対象ファイルを読む
     light → 01-draft.md
     full  → 02-letter.md ＋ 03-draft.md
3. モードに応じた項目を検査する
4. findings が空 → clear: true を書いて終了
5. findings がある → 該当箇所を修正して対象ファイルを更新
6. 再検査する
7. clear: true になるまで 5〜6 を繰り返す（上限なし）
```

**修正は最小限にする。** 該当箇所だけを直し、周辺の文章を書き換えない。

**`severity: review` の項目は修正しない。** 人間の確認に回す。`clear` の判定には影響させない。

---

## 人間に必ず見せるもの

`clear: true` になっても、**検出して修正した内容はダッシュボードの自動運転ログに必ず残す。**

このゲートは自動修正するが、何を消したかを人間が知らないまま運用するのは危険である。特に E1（偽の限定）は、書いた本人が「実行するつもりだった」場合に削除が誤りになる可能性がある。ログを見て復活させる判断は人間に残す。

---

## このスキルがやらないこと

- 法的助言はしない。弁護士ではない
- 表現の良し悪しの判断はしない。それは `letter-audit` の仕事
- グレーゾーンの議論はしない。**明らかな地雷だけを踏ませない**

判断に迷う表現を見つけた場合は、削除せずに `findings` に `severity: "review"` で記録し、人間の確認に回す。**迷ったら消すのではなく、迷ったと記録する。**
