# letter-audit

**このスキルは書き直さない。判定して差し戻すだけ。**

人間が最終確認をしない完全自動フローでは、機械が自分を落とす仕組みが必要になる。それがこのスキル。

## 絶対に守ること

1. **最初に `letter-meta.json` の `productType` を読む。** A3 と C2 の判定基準が型で変わる。**読まずに判定すると道具型が必ず落ちる**
2. **`critic` サブエージェントを使って実行する。** 親のコンテキストを渡さない。自分が書いた文章だと知っている状態では正直な×が出せない
3. **判定は真偽値で返す。** 「やや弱い」「もう少し」といった中間評価を作らない。○か×か
4. **×には必ず行番号と修正指示を添える。** 「改善の余地がある」だけでは差し戻せない
5. **褒めない。** 良かった点の列挙は不要。通過した項目は○とだけ書く
6. **×が1つでも残れば `pass: false`。** 15/16 は不合格

---

## 商品の型で判定が変わる

| 型 | 再現性の根拠 | 影響する項目 |
|---|---|---|
| `tool`（道具型） | 成果物そのものの検証可能性 | **A3・C2** |
| `experience`（体験談型） | 書き手の実績 | **A3・C2** |

16項目のうち **A3 と C2 の2つだけ**が型で分岐する。残り14項目は共通である。

**道具型に体験談型の基準を当てると、実績がないため C2 が必ず×になる。**
これは書き手の落ち度ではなく判定側の誤りなので、型を読まずに判定してはならない。

---

## 入力

- `notes/{slug}/02-letter.md` — レター本文（行番号付きで読む）
- `notes/{slug}/letter-meta.json` — 構造メタ。**`productType` と `toolEvidence` を含む**
- `knowledge/account.md` — 誰の目で読むか（ペルソナ）

---

## 出力

- `notes/{slug}/04-audit.md` — 人間が読む判定レポート
- `notes/{slug}/audit.json` — ワークフローが分岐に使う判定結果

```json
{
  "pass": false,
  "productType": "tool",
  "round": 1,
  "maxRounds": 2,
  "score": "13/16",
  "failures": [
    {
      "id": "C2",
      "label": "再現性がなさそう",
      "lines": [44, 52],
      "why": "「27本のスキル定義が入っています」と件数を書いているだけで、実物の断片が本文に無い。買う前に中身を確認できないため、道具型の再現性が成立していない",
      "fix": "スキル定義の実物を数行そのまま載せる。目次ではなく中身を見せる"
    }
  ],
  "returnTo": "sales-letter"
}
```

**`productType` を必ず出力に含める。** どちらの基準で判定したかが後から検証できなくなる。

---

## 判定16項目

### A. 欲しくさせる側（4項目）

| ID | 判定項目 | ×になる条件 |
|---|---|---|
| A1 | 理想の未来と再現性が交互に来ているか | 理想の未来が2つ以上連続、または再現性が2つ以上連続している |
| A2 | 最後が理想の未来で終わっているか | 締めが恐怖・注意書き・箇条書き・価格説明で終わっている |
| A3 | 再現性が4つで作られているか | **★型で分岐**。4つのうち欠けているものがある |
| A4 | 約束が「何でもできる」になっていないか | 効果を3つ以上並べている、または対象範囲を限定していない |

**★ A3の見分け方 — 共通の2つ**

- 単純化 = やることが1つに絞られているか。**5個並んでいたら×**
- 簡易化 = 時間・回数・期間の**具体的な数字**があるか

**★ A3の見分け方 — `type: experience` の2つ**

- 天井を下げる = 到達点が読者の手の届く高さか。**自分の最大実績をそのまま提示していたら×**
- 共感 = 自分がダメだった頃の**具体的なエピソード**があるか

**★ A3の見分け方 — `type: tool` の2つ**

- 成果物の開示 = **実物の断片が本文に出ているか**。目次・章立て・「〜が入っています」だけなら×
- 不便だった状況 = この道具がなかったときの**具体的な作業**が書かれているか。抽象的な述懐なら×

> `type: tool` で「天井を下げる」「共感」を探さないこと。
> 道具型にそれらを求めると、実績のない書き手は構造的に通せない。

### B. 恐怖（3項目）

| ID | 判定項目 | ×になる条件 |
|---|---|---|
| B1 | 恐怖は1つだけか | 2つ以上の地獄が描かれている |
| B2 | 「もう手遅れ」になっていないか | 「今からでは遅い」「既に手遅れ」に相当する記述がある |
| B3 | 何を地獄に置いたか。集まる客層は狙い通りか | 地獄の種類がペルソナの支払い意欲と矛盾している |

**B3の判定方法:** 地獄が「お金がない」なら、集まるのはお金がない人になる。`account.md` のペルソナの支払い意欲が中〜高なら矛盾するので×。地獄は「時間を失う」「後発に抜かれる」など、支払い能力のある層が反応するものに置き換えさせる。

### C. 買わない理由6つ（6項目）

| ID | 買わない理由 | ×になる条件 |
|---|---|---|
| C1 | そもそも問題があると思ってない | 問題の名指しが**状態**で書かれている（行動になっていない） |
| C2 | 再現性がなさそう | **★型で分岐（下記）** |
| C3 | 今買う理由がない | 期限・値上げ・特典終了のいずれも無い |
| C4 | 高いしあとでいい | 中身の分解が無い、または**値下げ・割引で解決しようとしている** |
| C5 | 自分には早い | 対象読者の明示が無い、または**向かない人を書いていない** |
| C6 | 本当に結果が出るのか | 「どこまでやれば結果が出るか」の到達点が示されていない |

**★ C2の判定 — 型で基準が変わる**

| 型 | ×になる条件 |
|---|---|
| `experience` | 天井を下げていない、または自分以外の結果が1つも無い |
| `tool` | 以下の**いずれか1つでも欠けたら×** |

`type: tool` で確認する3点:

1. **成果物の中身を開示したか** — 実物の断片が本文にあるか。目次だけなら×
2. **買った人が最初の1歩を踏めるか** — 「まず何をするか」が具体的に書かれているか
3. **動作条件・前提環境を明記したか** — 何があれば動くかが書かれているか

`letter-meta.json` の `toolEvidence` に該当行が記録されている。**記録された行を実際に読んで確認すること。**
メタが `true` でも本文に実物がなければ×である。

```
✕ 「27本のスキル定義が入っています」        → 開示していない
✕ 「すぐに使えます」                        → 最初の1歩がない
✕ （動作条件の記述なし）                    → 動く証明ができない
○ 実物の断片 ＋「まずこれをコピーする」＋「Pro プランがあれば動く」
```

**道具型で C2 が×になるのは、ほぼ例外なく中身を出し惜しみしたときである。**

> `type: tool` で「自分以外の結果がない」ことを理由に×にしないこと。
> 道具型は書き手の実績を根拠にしない設計であり、これを求めると構造的に通せない。

**C1の判定:** ブロック2の文を見て、読者が昨日か今日した（しなかった）**動作**が書かれているか。「〜な人」で終わる形容は状態なので×。

**C4の判定:** 「今だけ安く」「特別価格」で納得を作ろうとしていたら×。安いほど再現性の不安が増える。中身を分解して「これなら高いのは納得だ」に持っていくのが正解。

### D. 漏斗（3項目）

| ID | 判定項目 | ×になる条件 |
|---|---|---|
| D1 | 断定しているか | 「〜かもしれません」「人によります」で逃げている箇所がある |
| D2 | 外の選択肢に触れて消したか | 他のやり方に一度も言及していない、または言及しただけで消していない |
| D3 | 最後に提示する行動は1つだけか | 出口が2つ以上ある（買う＋フォロー＋登録 など） |

---

## 差し戻しのルール

```
round 1: ×あり → sales-letter に差し戻し（failures をそのまま渡す）
round 2: ×あり → 打ち切り。pass: false のまま人間に回す
```

**上限は2周。** v2.0 の3周から短縮した。トークン消費の削減と、3周目で通る確率が低いという判断による。

**2周で解消しない場合は自動修正を諦める。** 同じ指摘が2回残るのは、レターの問題ではなく上流の問題である可能性が高い。`04-audit.md` の末尾に「上流の見直しを推奨」と明記し、疑わしい工程名を書く。

| 残った項目 | 疑うべき上流 |
|---|---|
| C2（再現性） | `product-concept` — 商品の型が合っていない可能性。`tool` にすべきものを `experience` にしていないか |
| C3（今買う理由） | `pricing-strategy` — 本物の期限や値上げ計画がそもそも無い |
| C4（高い） | `pricing-strategy` — 価格と中身が釣り合っていない |
| C5（自分には早い） | `account-design` — 対象読者の設定が広すぎる |
| B3（客層） | `weekly-research` — テーマ選定の段階でずれている |

**差し戻し時は failures だけを渡す。** レター全文の書き直しを指示しない。○だった箇所を壊されると振り出しに戻る。

---

## 04-audit.md の形式

```markdown
# レター診断 — {slug} / round 1 of 2

型: tool（道具型）
判定: 不合格（13/16）

## × 残っている項目

### C2 再現性がなさそう
- 該当行: 44-52
- 状態: 件数だけを書いており、実物の断片が本文に無い
- 修正: スキル定義の実物を数行そのまま載せる。目次ではなく中身を見せる

## ○ 通過した項目
A1 A2 A3 A4 B1 B2 B3 C1 C3 C4 C5 C6 D1
```

**通過項目はIDの羅列だけでよい。** 説明を書かない。読むべきは×だけ。
